Operator, 2026-11-16: findings 9–15 of the "fully bake" review and its lower-impact items, each checked against the code before it was changed. Decisions **D1380–D1387** (D1388–D1399 unused). Migration **160** (160–164 are this lane's block). Threat rows **T700–T705** (THREAT_MODEL.md, "Bake fixes (lane bake3)").

## Decisions

| ID | Decision | Why |
| --- | --- | --- |
| D1380 | **The Bin knows the workspace modules' items.** `BinItem.type` takes the ten workspace Bin types (`WORKSPACE_BIN_TYPES`). Each reads its own kind (Form, Goal, Standup, Contact book, Contact, Company, Deal, Time project, Booking type, Townhall session) in the row meta and to screen readers, with its module's icon; a contact, company, or deal restores to its contact book and the rest to their module (a contact book said "Default" before: its provider sent no folder name). Under the core filters an **Apps** row of filter chips lists the modules that have items in the Bin (plus the active one), in Settings order. Each provider's list now carries `href`, the item's friendly in-app path (`formPath`, `goalHref`, `projectHref`, `checkinHref`, `typeHref`, `townhallPath`, the Contacts paths, `/contacts?book=<shortid>`); the restore toast offers **Open**, which goes through the app's guarded `nook:open-path` (D1260). | Before, every module item read "Item" with a box icon, and only "All" listed them. Seven always-on chips would double the filter row for modules most Bins never hold. The providers know their own paths; the Bin does not. |
| D1381 | **Settings → AI → Usage** (`/settings/ai/usage`, admins, as the whole page): the counts `GET /api/agents/admin/usage` already returned (runs, prompt and completion tokens per UTC day, per person or per agent), with a group choice, the last 7/14/30/90 days, four KPI tiles, a stacked chart of tokens per day (the module Insights chart, with its "Show as a table"), and a table of totals, most tokens first. It loads the first time its tab opens. No per-model split and no cost: `agent_usage_daily` records neither, and inventing a price table is out of scope. A full 2,000-row answer says the oldest days were cut. | OPERATIONS.md and USING.md described a screen that did not exist. |
| D1382 | **"Public townhall links" is its own workspace setting** (`publicTownhall`, `team_settings` key `public_townhall`), beside "Public forms and polls" and "Public booking pages". Migration 160 widens the key CHECK (12-step rebuild) and copies a stored `public_forms` value to it, so an upgrade keeps each workspace's behaviour; with nothing stored both read the default (on). `publicPolicyAllows("townhall_session")` reads it; the share sheet's hint and the POLICY_OFF message name it. A rename of the forms switch was the alternative; a separate switch was chosen because an audience link (anonymous questions and votes, live) is a different exposure from a form. | The forms switch silently closed townhall audience links, and the townhall hint pointed to a switch that never mentioned Townhall. |
| D1383 | **Week grids start on the viewer's "Week starts on".** `monthGridDays(month, weekStart)` and `weekdayLabelsFrom(weekStart)`; the shared `MonthGrid` reads the preference unless a caller passes it, and Calendar's month view passes the value it loaded its 42 days with; the in-app booking pickers (Book time, Reschedule) pass it to `SlotPicker` (which now takes Saturday too); the board timeline's Quarter week columns, its first range, and its growth use it (`weekStartOn`), and a range that does not start on the week start gets a part week first instead of shifted columns. Left as they are: public booking pages (no signed-in viewer; Monday), and report date presets (`shared/reportParams.ts`, ISO weeks, evaluated on the server for every viewer). | The preference changed only the schedule pickers and Time. |
| D1384 | **Admins reset a member's booking link name from the member's page** (Settings → Team → member): a "Reset booking link name" member action (Bookings module, admins only; the row variant shows nothing), with the current `/p/book/<name>`, asking first in the app's own dialog what the reset does (a new name from the member's name, the old link dead at once, the booking page's name, welcome text, time zone, and busy calendars back to the defaults; types and availability stay). It reads every member's name in one call, `GET /api/bookings/admin/handles?users=` (admins; 403 otherwise), and resets through the existing `POST /api/bookings/profile/:userId/reset-handle`, already audited (`bookings.handle_reset`). The reset's behaviour is unchanged (T579 relies on it). | The T579 control was API-only. |
| D1385 | **MCP restores what it bins.** `restore_form`, `restore_goal`, `restore_contact`, `restore_company`, `restore_deal`, and new `bin_time_project` / `restore_time_project`, `bin_townhall_session` / `restore_townhall_session`: the module's write scope plus `bin:write`; a bin counts against the Bin buckets, a restore does not; a restore takes the item's id and goes through the module's Bin provider (`restoreItem`), so who may restore and the NOT_FOUND parity are the REST Bin's (T148); none is offered to chat agents (`isBinTool`). Found on the way: the goals Bin provider called `restoreGoal(id, userId)` against its `(userId, id)` signature, so **every goal restore was NOT_FOUND**, in the app's Bin too; fixed and tested. | `bin_*` descriptions promise a restore that only notes, cards, rows, events, standups, and booking types had. |
| D1386 | **Dead slots and orphan endpoints, one by one.** `cardFaceBadges`: wired, Goals registers a card face goal badge (◎ and the goal's progress, or the count of goals) from a new batched read `GET /api/goals/for-cards?ids=` (≤ 200 cards, cards on boards the viewer can read and goals they can open, ≤ 5 goals a card); every badge on screen asks within one tick, answers are cached per card, and the card's Goals field forgets an answer when it changes. A badge with nothing to show leaves the card's footer line out (CSS), so cards look as before. `POST /api/refs/summaries` could not answer "which goals does this card feed" (it summarizes items, not links): kept as the chips' batch read for `src/ui/links` (another lane's area). Key result history: a sparkline on each key result, drawn from the goal's history the page already loads (one request, not one per key result); `GET /api/key-results/:id/values` stays as the documented per-KR read with a date range. `GET /api/tasks/cards/:cardId/children`: kept (documented, tested); the card dialog already lists sub-cards from the board's own data. `GET /api/checkin-rounds/:rid` and `/summary`, `GET /api/inbox/runs/:id`: kept (documented REST twins of MCP tools). Removed: `PUT /api/crm/pipelines/:id/stages` (a duplicate of PATCH; nothing called it), `GET /api/crm/search` (undocumented; nothing called it; MCP `search_crm` and the Contacts search scope use the service), and the `settingsSections` module field (no module declared it, nothing read it). `workKindRenderers` stays, documented as the link chips' icons and labels to come: the chips live in `src/ui/links`, another lane's area. | Each was either worth a screen or worth deleting; documented contracts stay. |
| D1387 | **CSV exports** for Goals (the list with its filters: `GET /api/goals/export.csv`), Standups (a standup's rounds' answers as the round page shows them: `GET /api/checkins/:id/export.csv`, one row per participant per round on a named standup, one per answer and no names or times of day on an anonymous one, nothing for a round under its threshold), Bookings (the list on screen: `GET /api/bookings/export.csv?view=`), and Tasks boards (a board's cards, archived ones with `?archived=1`: `GET /api/tasks/boards/:id/export.csv`). The Forms/Time pattern: UTF-8 BOM, CRLF, `csvCell` (formula-leading cells get `'`, T514), `no-store`, an attachment named from the item, at most 10,000 rows (the file says where it stopped), only what the caller can read through the same reads as the screen, audited (`goals.export`, `checkins.export`, `bookings.export`, `tasks.export`). In the app: "Export goals (CSV)", "Export answers (CSV)", and "Export … bookings (CSV)" in the module menu, and a download button beside Board settings. | The other modules had exports; these four did not. |
