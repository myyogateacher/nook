Notes, files, tasks, and more.

Nook is a secure, self-hosted workspace for a household or a small trusted team: Markdown notes with immutable versions, files in the same folders, task boards with subtasks and sprints, typed collections, shared calendars with reminders, a Today dashboard, a 30-day Bin, and an MCP server for trusted AI clients, all in one small Docker container.

Product

One workspace, several apps

Today opens each app after sign-in. Every app, folder, note, file, board, card, collection, and event has its own URL.

☀

Today

What needs you now: due and assigned cards, recent notes and drafts, files, rows, upcoming events, items leaving the Bin, and storage.

✎

Notes

An Outline-like Markdown editor with slash commands, checklists, code, images, tables, and PDF export. Publish immutable versions, diff, and restore.

▤

Files

Upload, preview, download, rename, move, and share documents in list or thumbnail grid view, with per-user quotas.

▥

Task boards

Columns with states and WIP limits; cards with due times, assignees, tags, flags, relations, comments, and attachments; column, table, list, and calendar views with shareable filters.

⋔

Subtasks and sprints

Task › Subtask, Epic › Story › Subtask, or your own levels, with subtask checklists and progress. Plan, start, and complete sprints with a progress strip.

◎

My work and views

Everything assigned to you across boards, and saved cross-board views shared privately, with chosen people, or with everyone.

▦

Collections

Typed tables for inventories, subscriptions, or recipes, with inline editing, saved views, CSV import and export, and view-only or can-edit sharing.

✐

Whiteboards

Sketch plans, diagrams, and floor plans with the Excalidraw editor, saved as .excalidraw files in your folders. Autosave, pictures from Files, links to notes and cards, version history, import, PNG and SVG export, cards in notes, view-only sharing, and pinch zoom on phones, with no outside requests.

⚿

Vault

Your services' secrets per environment, shared with people and groups per environment, with protected environments, import and export, versions, a generator, reveal that hides again, and the Bin. Encrypted at rest with a key you keep outside the data directory; anyone with the server and its key can read every secret.

◷

Calendar

Shared calendars, repeating events, links to notes, cards, and rows, reminders in the bell, by Web Push, or by email, and revocable feed links.

☷

Team roles

Admins, members, viewers, and guests. Viewers and guests are read-only, enforced on the server; admins invite people with single-use links and block accounts, but never see private content.

⌕

Full-text search

Accent- and case-insensitive search across note titles and bodies that respects sharing exactly.

♲

Shared Bin

Deleted notes, files, cards (with their subtasks), boards, collections, rows, calendars, and events wait 30 days, then are removed for good.

✉

Email that fits

Assigned to you, shared with you, comments, proposals, reminders, event changes, sprints, and security notices, grouped and deep-linked into the app, plus an optional daily or weekly digest at your local time. Per-kind switches, quiet hours, muting per board or calendar, one-click unsubscribe, and optional bounce handling. No trackers or images.

⇲

Agent inbox

Agents suggest cards, events, rows, comments, and note drafts; you approve or reject each one with a readable before-and-after diff. Routines keep scheduled prompts that your MCP client runs. Nothing changes until you say so.

⌁

MCP server

Trusted AI clients read and write over Streamable HTTP with revocable keys and per-key permissions for notes, files, tasks, collections, calendar, Today, and team.

⇄

REST API

The MCP tools over plain HTTPS at /api/v1 for scripts and CI: list what a key may call, run a tool with a JSON body, and get JSON back. Keys only in the Authorization header, never cookies or URLs, with their own rate limits.

⚿

Nook keys

One kind of API key with permissions per module, all or chosen folders, notes, files, boards, views, collections, calendars, routines, and whiteboards, MCP or REST, optional IP address limits, an expiry, rotation with a grace period, and narrowing without a password. Admins see every key in Team → Keys, revoke with a reason, and set policies (lifetime, required expiry, modules and MCP per role) checked on every call.

◫

Private sharing

One Access sheet everywhere: share with people and groups, each at Can view, Can comment, Can edit, or Manager where the item offers it, or with everyone signed in (guests excluded). Nothing is public.

▣

Mobile first

A multi-pane desktop workspace with focused phone screens, and working Back and Forward in every app.

◧

Modules

Settings → Modules turns apps off per account, on every device. It only hides them: data, sharing, and MCP access are unchanged.

◇

Portable storage

Readable Markdown and plain file bytes on disk, with SQLite for metadata and access rules.

⌘

Local security

Argon2id, encrypted TOTP, CSRF protection, strict CSP, hashed keys and feed tokens, and a hardened container. Change your password in Settings, or reset a forgotten one by email: the link lasts 30 minutes, still needs your two-factor code, and signs out every device.

⚡

Fast boards

A trimmed board payload keeps a 1000-card board light to load, on phones too.

What's new in v0.22.0

Shared vaults: access per environment, protected environments, import and export, data-key rotation, and Activity.

  • Shared vaults. Share a vault with people and groups per environment at none, read, write, or admin (viewers read at most; guests and integrations never). A people × environments grid on a computer, cards on a phone, a leave guard, one-save handover, and always at least one owner. Admins who are not members see nothing.
  • Protected environments. prod is protected by default: revealing, editing, exporting, or reading its history asks for your password again, once per 15 minutes per session.
  • Import and export. .env, JSON, and CSV with a preview; ten exports an hour, recorded in Activity; CSV formula cells neutralised.
  • Data-key rotation. Whenever anyone loses read, the vault's data key rotates in the background and owners get a bell notice to rotate the real credentials, with "Show what they read". Rotate on demand from the vault's settings.
  • Activity and history. An Activity page per vault, a version-history dialog with Show and Restore, a tag filter, "Shared with me", and a 64 MiB quota per vault creator.
  • For developers using MCP. Still no vault tools; nkv_ keys, REST, and MCP tools come next.
Upgrading: back up first with ./scripts/backup.sh --force; migration 037 runs on the first boot and only adds. See Upgrading.

What's new in v0.20.0

The Vault: your services' secrets per environment, encrypted at rest, owner-only in this first release.

  • Vault. A new app for your services' secrets with environments (dev, staging, prod, or your own). Each secret holds one value per environment, an encrypted comment, twenty kept versions, and the Bin. A secrets × environments grid on a computer; one environment's cards on a phone. Values stay masked until Reveal and hide again after 30 seconds, when the tab is hidden, or when the dialog closes; Copy clears the clipboard after 30 seconds unless you copied something else since. A generator makes passwords, tokens, and six-word passphrases in the browser. Saving into several environments at once checks every environment's version.
  • Encrypted at rest; anyone with the server and its key can read every secret. The Vault is for your services' credentials, not a personal password manager. Values and comments use AES-256-GCM under a per-vault data key wrapped by VAULT_ENCRYPTION_KEY; names and tags stay plain for search.
  • Off until you set a key. VAULT_ENCRYPTION_KEY (openssl rand -base64 32, different from the TOTP key) or VAULT_ENCRYPTION_KEY_FILE outside the data directory, so backups never contain it. verify-key checks it; rotate-kek re-wraps under a new key read from a file, refuses while a server runs, and prints fingerprints, never the key.
  • Owner-only for now. Another member, a viewer, a guest, or an admin who does not own a vault gets "not found" everywhere. Sharing per environment, import and export, nkv_ API keys, and MCP tools follow in the next two releases.
  • Also. SQLite runs with secure_delete on for every module, and the server keeps a server.heartbeat file in the data directory while it runs.
  • For developers using MCP. No new tools; no key can reach the Vault yet.
Upgrading: back up first with ./scripts/backup.sh --force; migration 031 runs on the first boot and only adds tables. The Vault stays off until you set VAULT_ENCRYPTION_KEY. See Upgrading.

What's new in v0.19.0

Integrations: accounts for AI clients and scripts that never sign in, reach only what is shared with them by name, and are keyed by admins.

  • Integrations (service accounts). Team → Integrations creates an account for a CI job, a bot, or an agent with a name and a role (member or viewer). Admins create, rotate, narrow, and revoke its API keys there with their own password. It never signs in: every sign-in path refuses it, and it gets no email or bell notifications.
  • Reach only what is shared with it by name. An integration is never part of "everyone signed in" and cannot join a group. Owners share with it from the Access sheet, where it appears under Integrations with a robot icon and an Integration badge, and the sheet says Admins hold its keys and can read what you share with it. Admins still never read anything that was not shared with the integration.
  • Attribution. Cards, comments, note versions, and whiteboards created through its key show its name with the badge; Team → Keys lists its keys with the integration as owner; GET /api/v1/me reports owner.kind: "service".
  • Blocking and deleting. Block pauses its keys at once. Delete revokes them and removes the account when it never had a key and created nothing; otherwise it stays as Deleted (kept for attribution) and can never be unblocked or re-keyed.
  • Leaving with a new key on screen asks first on the integration's page too, including browser Back on phones.
  • For developers using MCP. No new tools, and no tool creates or manages integrations or keys.
Upgrading: back up first with ./scripts/backup.sh --force; migration 036 runs on the first boot and only adds. Nothing about existing people or keys changes; no new settings. See Upgrading.

What's new in v0.18.0

API keys limited to chosen items in every module, a REST API for scripts and CI, address limits for keys, and a batch of small fixes.

  • Keys limited to chosen items in every module. An API key can now be limited to chosen folders and notes, folders and files, boards and saved views (only views you own, read only), collections, calendars, routines, and whiteboards. Every tool checks each item it touches: anything outside the key's choice answers "not found" as if it did not exist, and lists, search, Today, and counts include only the chosen items.
  • A REST API for keys. Scripts and CI jobs can call the same tools as MCP over plain HTTPS: GET /api/v1/me, GET /api/v1/tools, and POST /api/v1/tools/<name> with a JSON body of the tool's arguments. The tools, arguments, results, limits, and rules are the same as over MCP. Send the key only as Authorization: Bearer <key>; a key in a URL is refused. Every error has a stable code (AUTH_REQUIRED, KEY_INVALID, KEY_POLICY, IP_NOT_ALLOWED, KEY_IN_URL, NOT_FOUND, RATE_LIMITED, and for file uploads UPLOAD_NOT_FOUND, UPLOAD_CONFLICT, and UPLOAD_FAILED). See MCP server.
  • Where a key is used. Each key works over MCP (the default), REST, or both. Editing a key can only narrow this, without a password; to widen it, rotate the key or create a new one. Per-minute limits and "last used" are kept for each surface. Admins decide which team roles may use REST and MCP in Team → Policies (REST: admins and members by default).
  • Address limits for keys. A key can be limited to up to ten IPv4 or IPv6 addresses or ranges, offered only when TRUSTED_PROXY_HOPS is 1 or more. A refused call shows on the owner's key row and in its Recent activity section, with a shortened address; admins see it in Team → Access activity, without the address.
  • Rotating can change access. Because rotating asks for your password, it can now also change the new key's access, where it is used, and its allowed addresses, including widening them. Edit still only narrows, for example from all boards to chosen ones.
  • New optional setting TRUSTED_PROXY_ADDRESSES. The addresses or ranges your reverse proxy connects from; when set, forwarding headers are read only from those proxies. Set it as soon as TRUSTED_PROXY_HOPS is 1 or more; otherwise Nook logs a warning at startup and the app port must be reachable only through the proxy (for example "127.0.0.1:2026:2026" in compose.yaml). See Environment variables.
  • Small fixes. On a computer the Team pages and the Inbox scroll the list and the details separately; the Home header stays in place while Today scrolls; member pages no longer log a console error while Google sign-in is off; Back after deleting a note or file from its list no longer takes an extra step; the Publish version button is larger on phones; End, Home, PageDown, and PageUp scroll the Files list and long notes; an open Access sheet stops offering guests once sharing with guests is turned off; and Access activity lines read as sentences.
  • For developers using MCP. No new tools, and no tool on either surface deletes forever, shares, or manages keys. Invalid arguments now name the argument on every tool, the Bearer scheme is accepted in any letter case, and every key that does not authenticate answers the one code KEY_INVALID; the reason is shown only to the key's owner.
  • Not in this release. Service accounts.
Upgrading: back up first with ./scripts/backup.sh --force; migration 033 runs on the first boot. Existing keys are unchanged: they stay MCP-only with no address limit, and REST is off on new keys until chosen. One new optional setting, TRUSTED_PROXY_ADDRESSES. See Upgrading.

What's new in v0.17.0

Whiteboards: sketches, diagrams, and floor plans drawn with the Excalidraw editor, saved as files in your folders and served entirely from your own server.

  • Whiteboards. A new app built on the Excalidraw editor: shapes, arrows, lines, freehand drawing, text, colours, undo and redo, and Mermaid diagrams turned into shapes. The editor ships inside Nook and runs entirely from your own server: no requests to other sites, fonts included, and the content security policy unchanged. A browser downloads it only when someone opens a board. See Whiteboards.
  • Boards live in Files. Each board is a .excalidraw file in one of your folders and appears in the Files list with its own icon. Rename it, move it to another folder, download the .excalidraw file, export a PNG, or delete it to the Bin and restore it from there. Boards count toward your storage.
  • Saving. Changes save by themselves, at the latest every 5 seconds while you keep drawing. When the connection drops, a copy of your unsaved work is kept on the device and sent when the connection returns, even if you do not reopen the board. Leaving the page right after drawing keeps the change.
  • Two devices. If a board changed on another device, Nook asks whether to Reload latest or Save mine as a copy; nothing is overwritten silently.
  • Safety net. When a save empties a board, or leaves a board of 10 or more shapes with fewer than half of them, the version before is kept (the newest five per board), and the owner can bring it back with Restore previous version.
  • Sharing. Share a board with people and groups through the Access sheet. Only the owner edits; everyone else gets a view-only canvas with a banner naming the owner.
  • Search. Board names and the text on boards are indexed. For now you can search them through the web API and the MCP tool list_whiteboards; the Search screen in the app does not show whiteboards yet.
  • Around the app. Settings → Modules has a Whiteboards row (on by default), Today lists recent whiteboards, and on phones pinching zooms the canvas, not the page. See Modules.
  • API keys and MCP. Two new key permissions, Read whiteboards and Create whiteboards, and a key can be limited to chosen boards. New MCP tools list_whiteboards, read_whiteboard, and create_whiteboard; no tool edits, deletes, or shares a board. Existing keys gain nothing. See MCP server.
  • Not in this release. Images on the canvas, links from shapes to Nook items, embedding a board in a note, a full version history, importing .excalidraw files as boards, SVG export, and a whiteboards filter in the Search screen.
Upgrading: back up first with ./scripts/backup.sh --force; migration 030 runs on the first boot. The Docker image grows by about 26 MB. No new settings; if you ever changed the key modules in Team → Policies, tick Whiteboards there before keys can use it. See Upgrading.

Back no longer repeats a step after you delete the note or file you were viewing; lists of boards, collections, and calendars need fewer database queries; a missing file with an extension (such as /favicon.ico) answers 404 instead of the app page; /robots.txt asks search engines not to index Nook; and if the app fails to load, a short message suggests reloading instead of an empty page. No new MCP tools.

What's new in v0.15.0

Sign in with Google alongside or instead of a password, with profile pictures and safe rules for linking existing accounts.

  • Sign in with Google. The sign-in, register, and invite pages offer Continue with Google. A Google address with no account gets one automatically when registration would allow it: open registration, a valid invite, or the first account on an empty instance (which becomes the admin). Accounts with two-factor on still enter their Nook code after Google. See Accounts and sharing.
  • Sign-in methods. AUTH_METHODS is password (the default), google, or both, enforced on the server. password turns Google sign-in off; google turns off password sign-in, registration with a password, forgot and reset password, and password change. Upgrading changes nothing until you set it.
  • New settings. AUTH_METHODS (default password), GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET (both required for google or both, or the server refuses to start), GOOGLE_ALLOWED_DOMAINS (optional; restricts Google sign-in only, not password registration), and TRUSTED_PROXY_HOPS (0 to 5, default 0). See Environment variables.
  • Profile pictures. A Google user's picture replaces the letter in the header, Settings, Team, the Access sheet, card assignees and the assignee picker, and comment authors. The server downloads it and serves it from your Nook, so browsers never contact Google and the content security policy is unchanged; otherwise the letter is shown. Pictures live in the data directory and are included in backups.
  • Linking existing accounts. A Google sign-in links automatically only to an account whose address Nook has verified, and only when Google is authoritative for it (a Gmail address, or a Google Workspace account on the address's own domain); otherwise nothing changes and the person is told what to do. Password users link in Settings → Security → Link Google after confirming their password. An admin can allow a link from Team (once, within 24 hours), optionally resetting the account, and can allow re-linking for a recreated Google account. The host command line offers allow-google-link <email> [--reset | --keep-credentials] and unlink-google <email>.
  • New admin powers. Allow Google sign-in; Reset account for Google sign-in (signs out everywhere, revokes API keys and calendar feed links, removes the password and two-factor, makes everything the account owns private and removes its shares, revokes its open invites, and pauses its routines; content is kept), offered in the app only for accounts whose address was never verified and never for admins or accounts that were admins in the last 24 hours; Allow re-linking (when the new Google account signs in, the previous holder's sessions, API keys, feed links, and unused reset links end, and by default the password and two-factor too); and Unlink (the member is signed out everywhere). Each asks for your password (or a Google confirmation) and two-factor code, is recorded in Team → Access activity, and tells the member on the bell and, with email on, by security mail; a reset is also shown at their next sign-in. See Team.
  • Confirm with Google. Accounts that sign in only with Google have no password, so they confirm with Google (a fresh Google sign-in) where others give their password: a new API key, rotating a key, and two-factor setup.
  • Rate limits. Password sign-in, account creation, and invite preview are also limited per client address (20, 5, and 10 a minute), in addition to the per-email and instance-wide limits. Behind a reverse proxy, set TRUSTED_PROXY_HOPS so each visitor counts alone. See Network and HTTPS.
  • Fixes. After turning on two-factor, Settings stays open on the recovery codes (Copy all, Download, I saved them); before, they disappeared at once. No new MCP tools for sign-in or Google accounts, and API keys are unaffected. See Two-factor authentication.
Upgrading: back up first with ./scripts/backup.sh --force; migration 034 runs on the first boot. Nothing changes for sign-in until you set AUTH_METHODS, and admins gain new powers over Google sign-in. See Upgrading.

What's new in v0.13.0

Passwords you can change and reset, groups, and a level for each person on everything you share.

  • Passwords. Change your password in Settings → Security with your current password, plus a two-factor code when you use one; your other devices are signed out. Full-text search

The search box at the top of the note list searches the text of your notes, not just their titles.

Syntax

Every word must appear, in any order; case and accents are ignored, so creme finds “Crème”. The last word matches as a prefix while you type; end with a space for whole words. "double quotes" match an exact phrase. AND, OR, NOT, *, and title: are ordinary text. Link text, image descriptions, and code are searched; link addresses are not.

What you see

Your own notes are searched as last saved, including drafts marked Draft. Shared notes are searched as their latest published version; you never see someone else's draft. Binned notes are not searched. Title matches rank first, with a highlighted excerpt, folder, owner, and last edit.

Scope

Search covers the section you are in: All notes, Shared with me, or one folder. Search all notes widens it; opening a result from outside the section switches to All notes.

  • Ctrl+K (⌘K on a Mac) or / focuses search; Esc clears it; ↑/↓ and Enter pick a result.
  • On phones, Back from a note returns to the results with the query kept. The query lives in the tab's history state, never in the URL.
  • Up to 20 searches per 10 seconds per user (then title matches only, with a notice) and 200 characters per query. Files are not searched yet.

Inbox

The Inbox (the button next to the bell, or /inbox) collects changes your MCP keys suggest instead of making. Nothing changes until you approve it, and only you see your keys' suggestions.

Proposals

A key with Suggest changes (inbox:write) plus a module's read permission proposes cards, card changes and comments, events, rows, and note drafts with submit_proposals. Each one shows the agent's reason as plain text, what it changes, and a before-and-after table or a line diff.

Approve or reject

Approve applies the change as you, with your access; if the item changed since the agent read it, the proposal fails and nothing is applied. Reject takes an optional reason the agent can read. Approve all works one proposal at a time.

Today and the bell

Proposals awaiting you on Today replaces Drafts from agents. The bell says which key suggested how many changes; push for proposals is off until you turn it on. Proposals expire after 14 days.

Routines

A routine is a prompt you keep in Nook (Inbox → Routines, /inbox/routines) for an agent to run on a schedule. Nook only says when it is due; your MCP client runs it, and everything it suggests waits in the Inbox.

Set it up

Name, instructions, the kinds of change it may suggest, optional boards, calendars, collections, or folders it is pinned to, a schedule (daily, weekdays, weekly, hourly, or manual) in your time zone, an optional bound key, and a per-run limit (25 by default). Nook enforces the kinds, pins, and limit.

Run it

A client calls list_due_routines, start_run (a two-hour lease), submit_proposals with the runId, and finish_run with a summary. In Claude Desktop each routine is also a routine.<name> prompt. A run left open is marked abandoned and the routine stays due.

Review it

Proposals are grouped by run with its summary; the bell says "Weekly review suggested 4 changes" once per run. Each routine keeps its last runs with status, proposal and tool-call counts (counted by Nook), and duration.

Settings → Modules

Each module has a switch, and every module is on until you turn it off. The choice is saved to your account, so it follows you to every device.

  • Notes, Files, Tasks, Collections, and Calendar: turning one off removes its tile and Today sections; its links go to Home with a Turn on in Settings hint.
  • Search, Bin, Notifications, and Team hide their boxes, buttons, and pages. Deleting still uses the Bin, reminders still arrive, and roles still apply.
  • Back steps over pages of a module that is off, and Forward stops before them until you turn it back on.
Hiding is not a security boundary. Nothing is deleted, sharing is unchanged, and MCP keys and feed links keep working. Revoke a key or link to stop it.
Using Nook

MCP server

An authenticated Model Context Protocol endpoint over Streamable HTTP lets trusted AI clients read your workspace and, with the permissions you grant, write drafts, cards, rows, and events.

1

Create a key

Open Settings → API keys (/settings/keys), choose New key, and build its access one permission at a time (module, permission, all or chosen items) with an expiry. It is shown in full only once; Nook stores its SHA-256 hash and a short prefix, never the plaintext. Viewers can create read-only keys; guests cannot create keys.

2

Configure the client

Copy the ready-to-paste configuration. The endpoint is <your origin>/mcp and the key is sent as a bearer token:

{
  "mcpServers": {
    "nook": {
      "type": "streamable-http",
      "url": "http://localhost:2026/mcp",
      "headers": { "Authorization": "Bearer <YOUR_API_KEY>" }
    }
  }
}
3

Revoke when done

Use a separate key per client, treat keys like passwords, and revoke unused keys from the same screen.

PermissionWhat the client can do
notes:read, notes:write-draftList, read, and search published notes; create notes and folders and write drafts of your own notes. It never publishes.
notes:publishPublish a draft of your own note, only a revision the key has read. Opt-in, with a warning: shared notes become visible to their readers.
files:read, files:writeList files and folders and read text files up to 1 MiB; store text files, upload files through a one-time ticket, rename and move your own files, and create folders. Never shares or deletes, and refuses moves that would change who can see a file.
tasks:read, tasks:writeBoards, cards, comments, relations, subtasks, sprints, saved views, and cross-board query_cards; create, update, move, link, and comment on cards, plan them in sprints, manage tags and WIP limits, add and start sprints (owner only), and attach files. Never deletes.
collections:read, collections:writeQuery and read rows; add and change rows and create private collections. Never deletes or changes fields.
calendar:read, calendar:writeList calendars and events; create and change events and set your own reminders.
bin:writeMove notes, cards, events, and rows to the Bin and restore them, only together with that module's write permission. Nothing is deleted forever; at most 10 a minute and 50 a day per key, and Review → Restore all on the key undoes it.
today:readThe Today summary, limited by the key's other permissions.
team:readAdmins only: names, roles, and status of accounts.

REST API

A key whose surface includes REST calls the same tools over HTTPS: GET /api/v1/me, GET /api/v1/tools, and POST /api/v1/tools/<name> with a JSON body. Send the key only in the Authorization header; a key in a URL is refused.

curl -s -X POST "https://<your nook>/api/v1/tools/list_boards" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" -d '{}'

A key limited to chosen items (folders, notes, files, boards, views, collections, calendars, routines, whiteboards) sees only those in every tool, list, search, and Today section. Behind a reverse proxy with TRUSTED_PROXY_HOPS set, a key can also be limited to IP addresses.

Only what you can open. A key sees exactly what its owner may read, never anything in the Bin, and restricted items only as “restricted”. Each key is rate limited per minute and per day, and writes are recorded in the audit log with the key's id.
Self-hosting

Quick start with Docker

You need Git, Docker Engine, and Docker Compose. Bun stays inside the image.

1

Clone and configure

git clone https://github.com/pankajsoni19/nook.git
cd nook
cp .env.example .env
mkdir -p /srv/mynotes

Set MYNOTES_DATA_DIR=/srv/mynotes. The directory must be writable by UID 1000.

2

Secure trusted accounts

ALLOWED_EMAILS=you@example.com,partner@example.com
TOTP_POLICY=required
TOTP_ENCRYPTION_KEY=<openssl rand -base64 32>
Keep the encryption key. It is not included in data backups.
3

Build and start

APP_VERSION=0.22.0 GIT_SHA=$(git rev-parse --short HEAD) \
  docker compose up -d --build

Open http://localhost:2026. The first account can be created while the database is empty.

4

Verify

curl http://localhost:2026/api/health
docker compose ps
Why “mynotes” in paths? Internal identifiers such as mynotes.sqlite, the mynotes_session cookie, the mynotes container, MYNOTES_DATA_DIR, and the mynotes-* backup archives keep the original prefix for compatibility with existing installs.

Access

Accounts and sharing

Adding users

Add trusted addresses to ALLOWED_EMAILS, temporarily set ALLOW_REGISTRATION=true, restart, and let each person register. Disable registration afterward. New accounts get SIGNUP_ROLE (default guest; viewer or member also allowed) until an admin changes their role in Team.

Admins and recovery

Admins manage roles and blocks in the Team app. If the only admin was blocked or is no longer on ALLOWED_EMAILS, promote another account or unblock one on the host: docker compose exec mynotes bun server/team-admin.ts set-role user@example.com admin (or unblock, or list). The CLI cannot set a password: a forgotten password needs Forgot password? (with email on) or another admin account.

Google sign-in

Optional. Set AUTH_METHODS to google or both with an OAuth client whose redirect URI is APP_ORIGIN/api/auth/google/callback. Accounts are created automatically when registration would allow it (the first account, an invite, or open registration); GOOGLE_ALLOWED_DOMAINS keeps it to your company domains, two-factor still applies, and Google profile pictures replace the letter avatars, served by Nook itself.

Permission precedence

Everything is private by default. Folder access applies to inherited items, but an item's own sharing always wins. A person's level is the highest of their direct share, their groups, and everyone signed in, and their team role caps it. Nothing becomes public.

Authentication

Two-factor authentication

Users enroll under Settings → Security. The grouped setup key is entered once in an authenticator app. Sign-in uses the current six-digit code or one complete recovery code.

Recovery codes are encrypted. Viewing or replacing them requires a password and fresh TOTP code. Each works once.

Administrator reset

docker compose exec app bun server/reset-totp.ts user@example.com

This revokes the user’s sessions and requires fresh enrollment.

Data

Storage and migrations

On-disk layout

/data/
├── mynotes.sqlite (+ -wal, -shm)
├── notes/<note-id>/
│   ├── current.md
│   ├── draft.md
│   └── versions/000001.md
├── documents/
│   ├── objects/<document-id>
│   └── .staging/<document-id>.part
└── backup/

File names live only in SQLite; bytes are stored under server-generated ids. Uploads stream to .staging on the data volume, and a sweeper removes abandoned staging files at boot and hourly. The data directory is mode 0700; database and Markdown files are 0600; symlinks are refused.

Automatic migrations

Numbered migrations run transactionally before traffic is accepted and are recorded in schema_migrations. Released migrations are append-only.

One instance per data directory. Upload slots, locks, rate limits, and the sweeper live in the process. Never point a second container or a dev server at the same directory.
Operations

Backup and restore

The backup script briefly stops the app for a consistent snapshot of SQLite, notes, and files, verifies gzip, and keeps five archives. A second run within seven days is skipped unless forced.

./scripts/backup.sh
./scripts/backup.sh --force

Weekly cron (Sunday 03:00)

0 3 * * 0 cd /path/to/nook && ./scripts/backup.sh >> /srv/mynotes/backup/backup.log 2>&1

Restore into an empty directory

mkdir -p /srv/mynotes-restored
tar -xzf /srv/mynotes/backup/mynotes-*.tar.gz -C /srv/mynotes-restored
MYNOTES_DATA_DIR=/srv/mynotes-restored docker compose up -d --build
  • Archives include documents/objects but not documents/.staging.
  • Archive size and the time the app is stopped grow with stored files; gzip gains little on media, and five archives multiply the disk use.
  • Binned items are backed up like live ones. Anything deleted forever can survive in older archives for about five weeks.
  • Start only one Nook instance on a restored directory, with the same .env.
Store .env separately. Backups intentionally exclude it and its TOTP key.
Networking

Network and HTTPS

Compose publishes port 2026 for LAN access. Prefer Tailscale Serve or a TLS reverse proxy for HTTPS.

APP_ORIGINS=http://localhost:2026,http://<server-lan-ip>:2026,https://your-device.your-tailnet.ts.net
  • Use HTTPS for non-local access.
  • Set APP_ORIGINS to a comma-separated list of exact trusted origins; never a wildcard.
  • Keep COOKIE_SECURE=true with HTTPS.
  • Plain HTTP requires COOKIE_SECURE=false and is less safe.
  • Never serve the data directory as static content.
Security

Security model

Application

Argon2id passwords, opaque HttpOnly sessions, SameSite cookies, CSRF tokens, CSP, and authorised reads for every note, file, search result, and MCP call.

Data

AES-256-GCM TOTP data, hashed API keys, restrictive permissions, symlink refusal, atomic writes, and mutation locks.

Container

Non-root UID, read-only root, dropped capabilities, no-new-privileges, and a small tmpfs.

Supported shape: a single Docker Compose host using local SQLite/WAL storage. Rate limiting is in memory and does not coordinate across replicas.

Help

Troubleshooting

Container cannot write data

Ensure the host path exists and is writable by UID/GID 1000.

Login fails behind a proxy, Tailscale, or LAN address

Add the exact scheme, host, and port to APP_ORIGINS. Plain HTTP also needs COOKIE_SECURE=false; prefer HTTPS.

TOTP code is rejected

Synchronize phone and server clocks. Codes are one-time; use a fresh code or recovery code.

An upload is refused

The message names the limit: file size (MAX_UPLOAD_BYTES), your quota (USER_STORAGE_QUOTA_BYTES, which includes the Bin), or free disk space (MIN_FREE_DISK_BYTES).
