# Search everywhere (lane bake-search)

Audit findings: ⌘K could only "Search notes for …" although the server already searched every module (`scope=all`) and every workspace module declared a `searchRenderer` nothing read; cards, events, and chats were not searched; the link picker ("Link cards, notes, goals, or contacts") could not find notes, files, whiteboards, collections, reports, or cards, because only module hits had `{ kind, id, title, href }`; ⌘K's Recent knew boards, collections, and recently edited notes only.

Decisions **D1340–D1346**. Threats **T680–T682** (THREAT_MODEL.md). No migration (150–154 stay free). HTTP contract: API_CONTRACTS.md § "Search everywhere: cards, events, chats, and `ref`". Builds on WORKSPACE_MODULES.md §B.12 (search registry) and LEFT_NAV.md D1293 (the palette).

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| D1340 | **The palette searches every app.** With two characters or more, 250 ms after the last keystroke, `CommandPalette` asks `GET /api/search?scope=all` (`usePaletteSearch`); a newer query aborts the older request; answers are cached for the palette's life, so deleting back asks nothing. Results come after the local groups (Apps, Recent, Quick actions, Commands, led by the best match as before) and before **Search notes for "…"**, which stays as the last line and fallback. One group per app, headed by the app's sidebar label and drawn with its icon; rows come from the scope's renderer: a workspace module's `searchRenderer` (now read, `moduleResultRenderer`) or the built-in ones (`CORE_RESULT_RENDERERS`: notes, cards, events, files, whiteboards, collections and rows, reports, chats), at most five per app. A section shows only when its app is in the person's sidebar (`shownApps(tree)`: off modules, modules the server does not offer, and role-hidden apps are out), and a row without a safe relative href is dropped. ↑/↓ walk every group; the active option is kept by id, so results arriving never move the highlight. "Searching your apps…", a rate limit (429: "Searching too quickly", one retry after 3 s), or an outage show in a status line outside the listbox. The Search module (Settings → Modules) turns cross-app search off with Notes' box. A result already listed under Recent (same href) is not repeated. | One box for everything, with the registry the modules already fill. The debounce, abort, and cache keep a typist inside the shared 20-per-10-seconds budget. |
| D1341 | **Cards, events, and chats are searched on the server**, as built-in scopes `cards`, `events`, `chats`, in `scope=all` as Tasks, Calendar, and Chat. Cards reuse the relation picker's `searchCards` (titles or a key, `readableBoardPredicate`, T95); events are a title `instr` over `readableCalendarPredicate` (T61), a series one hit (`server/calendar/search.ts`); chats are the caller's own chats through `listChats(q)` (the chat FTS, owner-scoped), only while Chat is usable for their role (`mayChatNow`), never chats shared with them, nothing for guests. No new index: titles are short and the predicates already bound the scan; a migration was not needed. | The same read check as each list endpoint, inside the query before LIMIT, so nothing new is reachable through search (T681). |
| D1342 | **Every built-in hit carries `ref: { kind, id, title, href }`**, added beside the scope's own fields in the route layer (`withRef`), for single scopes and `all` alike; the underlying search functions (used by MCP and REST) are unchanged. `ref.kind` is a work kind (`note`, `card`, `event`, `document`, `whiteboard`, `collection`, `row`, `report`) or `chat`. The All scope's Collections section also finds **collections by name** (readable ones, ahead of row hits). The link picker's `candidateOf` reads `ref` when present (chats are not linkable) and shows a board, calendar, or collection as the subtitle, and a card's key. | One shape every consumer reads; additive, so existing clients and tests keep their fields. |
| D1343 | **Note links slug the published title.** `notePath` used `notes.title`, which follows the owner's draft; it now uses the current published version's title when there is one (the owner's unpublished note keeps its draft title, which only they read). Slugs are cosmetic (D773), so old links still resolve; the app canonicalizes. | Found while adding note refs: every server-written note link (search, link chips, mail, MCP) could show a reader the owner's unpublished title (T680). |
| D1344 | **Recent lists recently opened items of every kind.** App records each item page as it opens (`recordRecentPath` on the location: anything `parseWorkRef` reads, plus `/calendar/event/<id>`): per person in localStorage, newest first, at most 12, **kind and reference only** (id, short id, or card key; no titles). Each time the palette opens, `resolveRecentItems` resolves the list through the link resolver (`POST /api/refs/summaries` for known ids, `GET /api/refs/resolve` for the rest, whose ids are then kept), which applies each kind's read check: titles and hrefs are current, and hidden or missing items are dropped and forgotten. Only kinds whose app is in the sidebar show. They lead the Recent group; recent boards, collections, and edited notes follow unless already listed. | Validated when shown, as the finding asked; no server state, nothing sensitive at rest (T682). |
| D1346 | **No item twice, one icon map** (coordinator review of the first shots: "Atlas salary bands" showed under Recent and again under Notes, because the Notes list's href carries the folder and the server's does not). Palette entries that open an item carry `item: { kind, id }` (opened items, recent boards and collections, edited notes, every search result: its `ref`, else a module result's own `kind` and `id`); `withResults` walks every group in display order and drops an entry whose item (or, for entries naming none, href) an earlier group already showed, and a group left empty. Icons: `APP_ICONS` and `appIcon(kind)` in `src/ui/links/workIcons.ts` give each kind its app's sidebar icon (a note is the Notes archive icon); the palette's Recent and the link picker's rows use it, as the result groups already used the sidebar's; a test keeps the map equal to `MODULES`. Link chips keep their per-kind icons. | One item, one row; one icon per app wherever it is listed. |
| D1345 | **Friendly URL follow-ups stay deferred** (FRIENDLY_URLS.md follow-ups 1–3: folders, report folders and lists, cross-board task views). Each needs a `short_id` column with backfill and trigger on its table, a new resolver kind, parse and format branches in `src/router.ts`, and name registration in the loads that list them, plus the canonicalization tests: three migrations and router work across Notes, Files, Whiteboards, Reports, and Tasks. That is larger than this lane's S/M bar, and `src/router.ts` is shared with the other lanes running now. These are list pages, which people share far less than items; their UUID URLs work and stay valid. | Not contained; recorded so the next lane starts from the exact steps already in FRIENDLY_URLS.md. |

## Not built

- **A full results page (`/search?q=`).** The Search module has no route of its own (`routeApps: []`; it is Notes' search box and the palette's search). A page would be a new app route and screen; the palette's five per app plus each app's own search cover the need for now. Next step if wanted: a `search` route rendering `scope=all` with `limit` per scope and "See all in <app>" links.
