# Card priority (lane PRIORITY)

Operator, 2026-11-16: a task card's "Urgent" flag becomes a proper **priority** with the values Urgent, High, Medium, and Low (plus none), chosen from a dropdown on the card, shown compactly on card faces, rows, and the table, and filterable and sortable on the board.

Decisions **D1310–D1319** (D1300–D1309 are a parallel lane's). Migration **123** (123–129 are this lane's block; 122 is the sidebar). No new threat: a priority is one bounded value per card, written at the card's edit level like every other field ([WAVE_13_TASK_CARD_UX.md](WAVE_13_TASK_CARD_UX.md) D110 still governs the remaining flags).

## Decisions

| ID | Decision | Why |
| --- | --- | --- |
| D1310 | **A card has one optional priority**: `cards.priority` is NULL (none) or `urgent`, `high`, `medium`, `low` (a CHECK lists them), shared as `TASK_PRIORITIES` in `shared/taskQuery.ts`, most pressing first. It is a card field (D107): set and cleared through `POST /boards/:b/cards` and `PATCH /cards/:k { priority }` at the card's edit level (view and comment levels are 403 `READ_ONLY`), with `revision + 1` and the CARD_CHANGED compare-and-swap, audited in `task.card_create` / `task.card_update { priority }`. Every card read carries it; the board payload sends it only when set (the D113 trim, as for `estimate`). `Urgent` leaves the flag set, which is now `blocked`, `needs_review`, `on_hold`. | A priority is ordinal and exclusive (a card is not both High and Low), so one column fits better than more flags. Keeping the four common levels (Linear, Jira) and "none" covers triage without a setting. |
| D1311 | **Migration 123** adds the column, sets `priority = 'urgent'` on every card with an `urgent` row in `card_flags`, and deletes those rows; Blocked, Needs review, and On hold rows stay. The `card_flags` CHECK still lists `urgent` (a 12-step rebuild for a value nothing writes is not worth it); the server never stores it (D1312). Card history is not rewritten: old "flagged this Urgent" entries still read that way. Transactional, filesystem-free, idempotent. | Converts existing data in place so nobody loses their urgent cards, without touching history. |
| D1312 | **The Urgent flag stays accepted on writes, as a deprecated alias.** `flags: [..., "urgent"]` on REST create/patch and on MCP `create_card`/`update_card` sets the priority to Urgent (unless the same write sends `priority`, which wins) and is dropped from the stored flags; responses never list `urgent` among `flags`. Sending flags without `urgent` leaves the priority alone, since a client that predates priorities never sees Urgent among the flags it reads back. Repeats and unknown flags are still 400. | Integrations and agents written against the flag keep working instead of failing with 400. |
| D1313 | **`flag:urgent` in the grammar means the Urgent priority.** The parser rewrites a `flag:urgent` term that has no other value (negated or not) to `priority:urgent`, so older links (`?flag=urgent`, `?q=flag:urgent`) and saved views stored with it read and run in today's words; stored view queries are not rewritten. Mixed with other flags (`flag:blocked,urgent`) it stays a flag term, since one term cannot OR two keys, and every matcher (the server compiler, MCP `list_cards` SQL, the client's structured and in-memory pipelines) reads its `urgent` as `priority = 'urgent'`. MCP `list_cards` `flags: ["urgent"]` likewise. `flag:none` now also matches urgent cards with no other flag. | Old links and views give the same cards they did; the canonical form moves to the new key. |
| D1314 | **History**: a `priority` change kind (`from`/`to`: `id` the value, `label` its word; null = none) recorded from the card's snapshot in the same transaction as the write, so REST, MCP, proposals, and the deprecated flag all record it. It coalesces like other fields (two quick changes by one person are one entry; a change that undoes itself vanishes). The app reads "set the priority to High", "changed the priority from High to Urgent", "cleared the priority (was Low)". | The same extension point as start dates and estimates (`shared/cardActivity.ts`). |
| D1315 | **Filtering**: the grammar's `priority:` key takes `urgent`, `high`, `medium`, `low`, `none` (values OR, `-` negates), in the server compiler, the board's in-memory matcher, and saved views; the structured filter has `priorities` (MCP `list_cards` takes `priorities`). The board's **+ Filter** menu offers **Priority** after Tag and before Flag, a multi-select of Urgent, High, Medium, Low, and No priority, each with its icon, kept in the URL as the canonical `?q=priority:…` like every other field; Tasks home and saved views offer it too. A view's single priority starts a new card with that priority (D637). | One grammar for URLs, saved views, the query API, and MCP (D137). |
| D1316 | **Sorting**: `sort: "priority"` on `POST /query`, saved views, MCP `query_cards`, and the home's Sort menu (Urgent first, then High, Medium, Low, then cards without a priority; ties by due date); the board's table gets a sortable **Priority** column (`sort=priority:asc|desc`, cards without one last both ways) and the list view can **group by priority**. No new sort mechanism: these are the existing ones. | Triage reads top-down; "none last" matches the due and estimate sorts. |
| D1317 | **In the app**: the card dialog and page show a **Priority** field after Start and Due, before Assignees (read-only roles see the word), using the app's `Select` (no native select, D91; keyboard and type-ahead, a sheet on phones) with No priority, Urgent, High, Medium, Low. Icons: Urgent keeps the old flag's red flame; High, Medium, and Low are three rising bars with two, one, or no bars dimmed, in orange, yellow, and muted blue (dark-only literals beside the flag tones in `tasks.css`). Card faces, list rows, the calendar, the timeline, and Tasks home show the icon alone before the flags (named "High priority" for screen readers; the card's accessible name reads it); the table shows icon and word; nothing for none. The composer carries a priority into its one create call. The Flags field drops Urgent. | The bars stay legible at 14 px for every level (lucide's signal icons draw Low as a single dot). |
| D1318 | **MCP and the rest**: `create_card` and `update_card` take `priority` (null clears it); `list_cards`, `get_card`, the write results, `query_cards`, and approval previews of card proposals carry it; `list_cards` takes `priorities`. No new tools (and none named delete or remove). The `tasks.cards` dataset adds a `priority` dimension; saved views' `fields` may list `priority`. REST v1 runs the same tools. | One field everywhere a card's fields are. |
| D1319 | **Out of scope**: a per-board priority scale or custom levels, priority roll-ups onto parents, notifications on priority changes (flags never notified either), and rewriting stored view queries or history. | Keep the lane small; none needs a schema change later. |
