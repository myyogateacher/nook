# Renaming Notes and Files folders (lane A, branch `feat/folder-rename-chat-nav`)

Operator request: Reports folders could be renamed from the sidebar's ⋯ menu, but Notes and Files folders could not. Add rename for both, in the sidebar, the phone drawer, and the phones' Folders panels, with the server's rules and an MCP tool.

Decisions **D1300–D1302** (D1303–D1304 are this lane's Chat sections, in docs/plan/LEFT_NAV.md §7; D1310 and up belong to another lane). No migration (`folders.name` and `updated_at` already exist). HTTP contracts: docs/plan/API_CONTRACTS.md § Files → "Folder rename and move"; MCP: `rename_folder` in the write-tools table.

## Decisions

- **D1300 — One service, owner-only, create's rules.** Notes and Files read the same `folders` rows, so one route renames for both: `PATCH /api/folders/:id` (which already took `name`) now goes through `updateFolder` in `server/folders.ts`. Only the folder's owner renames it. A recipient of a shared folder gets the usual 404, at **edit** too: an edit share edits the notes and files inside, while the folder itself (create, move, rename, delete, sharing) stays the owner's, as create and move already were. Viewers and guests get 403 `ROLE_READ_ONLY` from the role write gate. The name follows `POST /api/folders`: trimmed, 1–120 characters, "Default" in any case is 409 `NAME_TAKEN`; sibling names may repeat, as on create (no uniqueness rule existed to copy). The Default folder answers 409 `DEFAULT_FOLDER` (the message is unchanged, the code is new) and the Attachments folder 400 `SYSTEM_FOLDER`. The answer now carries the folder (`{ ok: true, folder }`). Audit, ids only and only when something changed: `folder.rename { folderId }`, and `folder.move { folderId, parentId }` for the move the route already did (it was not audited before). No item activity: folders are not workspace-module items.
- **D1301 — MCP `rename_folder`.** `notes:write-draft` or `files:write` (as `create_folder`), the `structure_write` daily bucket, item-scoped on `folderId` (a chosen-folders key renames only folders in its reach). Same validation and service as the route; refusals map to `NAME_TAKEN`, `NOT_FOUND` (someone else's folder, shared or not), and `INVALID` with `reason` `DEFAULT_FOLDER` / `SYSTEM_FOLDER`. Allowed for chat agents (`NOOK_AGENT_TOOLS`) like `create_folder` and `rename_file`. The name has no delete or remove in it.
- **D1302 — In place, from a ⋯ menu or F2.** Folder rows in the sidebar tree (`SidebarFolderTree`'s new `rename` prop), the phone drawer, and the phones' Folders panels (Notes' and Files') get the Reports folder ⋯ menu component (`ReportOverflowMenu`; its CSS moved to `src/reports/overflowMenu.css`, loaded with the component, so Notes and Files draw it without reports.css) with **Rename**, on exactly the folders the server lets this person rename (`canRenameFolder`: a writing role, their own, not Default, not Attachments). F2 on a folder row in the sidebar does the same; right-click keeps the browser's own menu (the rows are real links: Open in new tab, Copy link). The row turns into an inline field (a form with `noValidate`, `maxLength` 120) with the name selected: Enter or leaving the field saves, Escape cancels; a blank or unchanged name saves nothing. Escape is caught natively so the phone drawer stays open, and the menu sits in `data-keep-drawer` so choosing Rename does not close it. The new name shows at once (`useFolderRename`, `src/shell/folderRename.tsx`); a refusal puts the old name back, unless something newer renamed it meanwhile, and shows the server's message in an error toast. In the sidebar the Share button sits just before the ⋯; in the drawer the ⋯ always shows at 40 px and Share stays in the Folders panel.
