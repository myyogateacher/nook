# Waves 45–48: Analytics reports (module `reports`)

Plan of record for the analytics reports module, condensed from the approved plan of 2026-10-12. **Ids corrected at kickoff (2026-10-13):** the migration is **050** (049 was reserved for the Messages module, then v0.37.0 took it for `attachment_undo_records`, so Messages moves to **053**, then **054** when wave 48b took 053 for `report_model`; **051** was reserved for wave 48's `report_instructions` and `report_versions`; wave 46 took 051 for the `agent_runs.via` word, so wave 48 uses **052**); decisions start at **D410**; threats start at **T356** (they started at T355 until v0.37.0 took that id for attachment Undo; renumbered when main was merged).

## What it is

A person pastes a link to a document (Outline or another doc system, reached through that provider's MCP server configured as a Tool Server). The document describes ClickHouse analytics: table definitions, rules, and metric definitions. Nook's AI writes ClickHouse SQL, runs it, and builds a web report with charts. Refresh re-runs the saved SQL without the AI, on demand or on an optional cadence.

Operator decisions (2026-10-12): ClickHouse is a built-in data source (admin-configured, encrypted password); a report is a saved, refreshable spec; doc MCP auth is bearer / API key only; scheduling is possible in v1 and optional per report.

## Decisions (D410–D429; wave 48: D450–D461)

| D410 | The module id is `reports` (label Reports, launcher `/reports`, routes `/reports` and `/reports/:id`); guests never have it (`features.reports`, routes 404). Migration 050 creates every table waves 45–47 use; 051 is reserved for wave 48. |
| D411 | The SQL guard refuses what it cannot read the way ClickHouse does: `#` comments, nested `/*`, heredocs and `$`, `{}` parameters, backslashes outside strings and any backslash inside a quoted name (review H2), non-ASCII outside strings and quoted names, control characters, and more than one statement. Banned anywhere in a select: INTO, OUTFILE, INFILE, SETTINGS, a FORMAT clause, EXPLAIN/SHOW/DESCRIBE as subqueries, and functions by exact name or prefix (`url`, `file`, `input`, `mysql`, `postgresql`, `jdbc`, `odbc`, `merge`, `loop`, `dictionary`, `format`, `generateRandom`, `hostName`, `getMacro`, `hasColumnInTable`, `s3*`, `remote*`, `cluster*`, `hdfs*`, `azure*`, `iceberg*`, `deltaLake*`, `hudi*`, `dict*`, `joinGet*`, `sleep*`, `filesystem*`, `mergeTree*`, `executable*`, …), whether named bare or quoted. `format` is banned only as a table function (after FROM, JOIN, or a FROM-list comma, and as a TABLE_FUNCTION node in the query tree); the string function `format('{} {}', a, b)` is allowed (Lane F, 2026-10-14). |
| D412 | Selects run as `SELECT * FROM (\n<statement without comments>\n) LIMIT max+1`. Before running, `EXPLAIN QUERY TREE` of the statement is the authority on which tables, table functions, and functions it reads; it runs with `result_overflow_mode=throw`, a 20,000-row and 8 MiB cap, and reaching either refuses the query (review H1); a ClickHouse without the analyzer fails closed; its errors are generic when they name anything off the allowlist (review M2). The lexer also checks comma-joined tables and `[GLOBAL] [NOT] IN <table>`. SHOW CREATE needs TABLE (review M1). The metadata class reads the five allowed system tables through subqueries filtered with `match(database || '.' || table, <allowlist RE2>)`, so joins and aggregates never see another table; SHOW DATABASES and SHOW TABLES rows are filtered after the read. |
| D413 | Allowlists are databases or `db.table` globs (`*`, `?`), case-sensitive, at most 100; `system` and `information_schema` can never match (a database glob that could, such as `*`, is refused). |
| D414 | Every query carries the per-query settings above. A user whose profile has `readonly=1` refuses them, so Test connection warns that the profile needs `readonly=2`. |
| D415 | A data source password is sealed with `server/agents/secrets.ts` under AGENT_SECRETS_KEY (owner `datasource`, AAD bound to the row), write-only (`hasPassword` only), never in the URL, audit, or logs; `agent-admin.ts rotate-key` and the startup check include data sources. |
| D416 | The schema catalog keeps at most 20,000 allowlisted tables per data source (500 on the SHOW/DESCRIBE path) and re-filters every read by the current allowlist. FTS ranks table names (×10) over table comments (×3) over columns (×1), an exact `table` or `db.table` first; every query term is quoted, so FTS operators are words. |
| D417 | The schema tools are plain server functions in wave 45: `sample_rows` reads at most 5 rows with `max_rows_to_read=100000` and `read_overflow_mode=break`; `run_schema_query` runs the metadata class only, 200 rows; `estimate` is `EXPLAIN ESTIMATE` of a select. |
| D418 | Wave 45 reports are private to their owner (missing and forbidden are the same 404). Search is title-only (`/api/search?scope=reports`, the list's filter): SQL, results, and docs are warehouse data and never searched. |
| D419 | Reports use the Bin (type `report`, folder "Reports"); purging cascades to snapshots, queries, runs, results, and the schedule, and 050's trigger removes key grants naming the report. |
| D420 | MCP in wave 45 is `list_reports` and `list_report_datasources` (names and default database only) under `reports:read`; `reports:write` exists as the pair's write half with no tools until wave 48; no scope ever runs ad-hoc SQL; neither tool is offered to chat agents (`NOOK_NEVER_TOOLS`). |
| D421 | At most two guarded queries run at a time per person and eight per server (429 `BUSY`); the console is audited with the query id and the statement's SHA-256, never its text. |
| D423 | Review fixes: a data source's stored password is cleared when its URL's host changes (unless a new one comes with the change); SHOW rows are filtered before the row cap; the Schema browser routes count against the query limit; the console has Cancel (abort plus `KILL QUERY`); `report_runs.doc_snapshot_id` and `BlockProvenance.docSnapshotId` record the doc a run used. `agent_runs.via` gets its `reports` word in 051, since 039's table is released. |
| D422 | Settings → Report data sources is an admin section of the Settings hub (`/settings/datasources`); saving a data source with an allowlist starts a schema sync in the background. |
| D424 | Wave 46, the doc: read by `docSource.ts` through a tool server the person may use, before any model call. Auto-pick `fetch`, `get_document`, `read_document` (the first whose schema takes `id` or `url`); a `resource` property means Outline's `{resource: "document", id}`; the person may name the tool and argument (`reports.doc_tool`, `doc_arg`). Only tools whose effective policy is `auto` (read-only by the server's word, or an admin's explicit auto) are offered, auto-picked, or called; an override naming any other tool is 400 `DOC_TOOL_REFUSED` (review M2). | D425 | A generation is an `agent_runs` row `via = 'reports'` (051), with no key or chat, run on the default provider by someone whose role may chat, under the daily budget (checked before and between steps), one at a time per person and under the report's one-run lock; its events are on `/api/runs/:id/events` for its owner only; the Audit log shows it as "Report generation". |
| D426 | `loop.ts` `toolChoice`: per step `auto`, `required`, or `{name}`; a named choice offers only that tool, also on the last step; a provider with `compat.namedToolChoice: false` gets `required` with that one tool; a call to another tool under a named choice is not run, and the named tool is exempt from the per-run cap; a tool result may `stop` the run. ## Lane E: generator reliability (2026-10-14)

Reports that are well formed can still be wrong. In order, each pushed on its own:

- **E1 eval** (`scripts/reportEval.ts`, `evals/reports/`): ten cases (doc, seed of an `eval_<case>` database, expected facts) run through the real generation path and scored on the persisted results; golden and trap specs check the cases themselves; docs/OPERATIONS.md "Report generation eval".
- **E2 result sanity checks** (`server/reports/sanity.ts`, `sqlShape.ts`): after a submit's queries ran and passed the design rules, `validateSpec` (when the generation asks for it) checks join fan-out (a guarded sample of the joined table's key, FINAL on collapsing engines, at most 4 extra queries), KPI-vs-breakdown reconciliation (same additive expression, or the plan's metric), coverage (holes in a time series, a series that starts or ends inside its literal date range, an empty KPI over a range), and units (percent over 1, a ratio with unit %, cents shown as currency, an all-zero or all-NULL measure). Hints start `sanity <check>:`; they refuse a submit once per run without using a try, and a second submit with the same hints is saved. Each round is a step in Runs (`[Nook checked the results: …]`), an audit entry `reports.generate.sanity`, and one log line per check in the reports scope.
- **E3 ClickHouse error repair hints** (`server/reports/repairHints.ts`): the runner attaches a hint to a failed query (`details.hint`; run_sql and the submit errors carry it to the model, the console's API answers with it). UNKNOWN_IDENTIFIER / UNKNOWN_TABLE / UNKNOWN_DATABASE: the three closest catalog names (edit distance with a bonus for shared name tokens); type errors: a cast; CANNOT_PARSE_*: date literals and `…OrNull`; ILLEGAL_AGGREGATION: HAVING; NOT_AN_AGGREGATE: GROUP BY or aggregate it; memory, rows, bytes, and time limits: the tables' partition and sorting keys from the catalog; ILLEGAL_FINAL: which table's engine lacks it. A query that reads a ReplacingMergeTree (or another collapsing engine) without FINAL gets a FINAL note, on a run_sql that worked too, and a `sanity final:` hint on submit. The tree check still never shows ClickHouse's text (review M2): the hint names only catalog tables and columns and identifiers that appear in the query. Tests use error texts captured from ClickHouse 26.6 (`tests/fixtures/clickhouse-26.6/errors.json`).
- **E4 metric catalog** (migration **058** `report_metric_catalogs`; `server/reports/metricCatalog.ts`, `shared/reportsMetrics.ts`, `src/reports/MetricsSheet.tsx`): once per doc snapshot, before planning, generation asks the report model to record the doc's metric definitions with a forced `record_metrics` tool (name, definition, expression, db.table, required filters, FINAL, grain, unit, time column; at most 24), then checks each: the table is in the allowlisted catalog, FINAL fits its engine, the time column exists, and `SELECT <expression> FROM <table> [FINAL] WHERE <filters> LIMIT 0` passes the guard and runs (a failure is kept as the metric's problem, with E3's hint). It is stored as a version with its snapshot and doc hash (owner-only; 20 versions kept); the newest version for the doc's hash is used, so the owner's edits stay until the doc changes. The prompt (generation and edits) lists the catalog; plan todos carry `metricId` (by id, or matched by name; an unknown id is refused); on submit, a done todo's query must contain its metric's expression, filters, and FINAL (`sanity metric:` hint, refused once like E2). Each metric keeps the doc's text that defines it (`excerpt`), and "Doc changed" names the metrics whose text changed or vanished in the new snapshot. ⋯ → Metrics (the owner's): a wide panel at the right (full screen at 390, Back closes and Forward reopens), each metric with its check state, Edit / Add metric / Remove, older versions read-only with Restore; `GET/PUT /api/reports/:id/metrics` (PUT with `expectedVersion`, 409 STALE). Not covered: definitions that live only on a linked page are not extracted (generation still reads the page).
- **E5 model fallback** (Settings → AI → "Fallback model for reports", agent settings `report_fallback_provider_id` / `report_fallback_model`, added to `agent_settings`' CHECK by 058; off by default): when a generation's model ends without a saved report after its submit tries, its nudges, or its steps (not a stop, a timeout, the budget, or a provider error), the run starts over once on the fallback (`reportFallbackFor`: never the primary itself) with a new plan and its own tries. A `[Nook retried on the fallback model …]` step, an audit entry `reports.generate.fallback`, and the run's `agent_runs.model` / `provider_id` say so (Runs shows the model that ran last); every saved block's provenance carries `model`, shown as "Model" in Inspect → Provenance. Edits do not fall back and do not stamp a model yet.
- **E6 (leftovers of E2, E4, E5)**: `validateSpec` scopes the sanity checks for an edit to the blocks it adds or changes and the queries they (or it) use; the edit agent refuses a patch once on them and on the catalog (`sanity metric:`, its plan todos carry `metricId`), and a manual SQL edit is saved with them as `warnings` (the route and `update_report_query`). Metric extraction also reads linked pages: Nook notes the doc links to are read through the run's doc tools first (when read_note is allowed; recorded in `report_doc_pages`), with the pages earlier runs read, and a metric defined there keeps the page's title (`page`; "Doc changed" leaves it to the page). MCP: `get_report_metrics` (reports:read, the owner's) and `update_report_metric` (reports:write, changes or adds one metric, re-checked, a new version, never removes, audited `via: "mcp"`). The edit agent falls back like generation; `commitSpec` stamps the run's model on the blocks an agent run writes; Runs shows every model a run used, in order, from its `reports.generate.fallback` entries (`models`).
