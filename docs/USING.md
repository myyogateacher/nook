# Using Nook

This guide covers the apps a signed-in user sees. Your server may use its own name in place of "Nook" (the operator's `APP_NAME`): it appears in tab titles, the sign-in page, **Settings → About**, and email. For installing, configuring, backing up, and upgrading a server, see [OPERATIONS.md](OPERATIONS.md). The same material is published at [pankajsoni19.github.io/nook](https://pankajsoni19.github.io/nook/).

## Home and URLs

Signing in lands on **Home**, which is also **Today** (below): a row of app links (Notes, Files, Tasks, Collections, Calendar) under the greeting. The account row at the top of Today, Tasks, Collections, Calendar, and Settings holds, from left to right, **Settings**, **Inbox**, the notification bell, your picture and name, and **Sign out**, always the rightmost (inside Settings the **Settings** button is left out). The Bin and Team are in [Settings](#settings), not in the top bar. On a phone the same buttons show as icons in the same order, with your picture in place of your name. Notes and Files keep Settings and Sign out in the sidebar footer instead (Notes also has the **Inbox** row there), and Files has the bell in the file list header next to **Upload**. Each app's **Home** control leads back. Each view has a real URL, and reloading or opening a link resumes that view (a signed-out visit shows the login screen first, then continues to the requested page):

| URL | View |
| --- | --- |
| `/` | Home |
| `/notes` | Notes, all folders (resumes your last note when no folder or note is named) |
| `/notes/folder/<folder-id>` | Notes in one folder |
| `/notes/shared` | Notes shared with you |
| `/notes/<note-id>` | One note in the editor |
| `/files` | Files, all folders |
| `/files/folder/<folder-id>` | Files in one folder |
| `/files/shared` | Files shared with you |
| `/files/<file-id>` | One file's preview and details |
| `/tasks` | Tasks home, Boards: your boards and boards shared with you |
| `/tasks/my` | Tasks home, My work: cards assigned to you on every board |
| `/tasks/views`, `/tasks/views/<view-id>` | Tasks home, Views: your saved views, and one view |
| `/tasks/<board-id>` | One board (the view, grouping, sort, filters, and sprint ride along in the query) |
| `/tasks/<board-id>/sprints` | The board's Sprints sheet, open over the board |
| `/tasks/<board-id>/card/<card-id>` | One card, open over its board |
| `/tasks/<board-id>/card/<card-id>/full` | One card as a full page |
| `/collections` | Collections: yours and those shared with you |
| `/collections/<collection-id>` | One collection's table (a card list on phones) |
| `/collections/<collection-id>/view/<view-id>` | A saved view of a collection |
| `/collections/<collection-id>/row/<row-id>` | One row (a side pane on desktop, a full screen on phones) |
| `/calendar` | Calendar agenda |
| `/calendar/month/<yyyy-mm>` | One month |
| `/calendar/event/<event-id>` | One event |
| `/notifications` | Your notifications |
| `/settings` | Settings (the section list on phones; Security beside the list on a computer) |
| `/settings/<section>` | One Settings section: `security`, `notifications`, `access`, `keys`, `modules`, `about` |
| `/settings/bin` | The Bin, in Settings (the old `/bin` still works) |
| `/settings/team/members`, `/settings/team/members/<user-id>` | Team in Settings: everyone, and one person's page |
| `/settings/team/<section>` | A Team section (admins): `invites`, `groups`, `integrations`, `keys`, `policies`, `templates`, `activity`, `email` |
| `/inbox`, `/inbox/history` | Inbox: proposals waiting for you, and resolved ones |
| `/inbox/p/<proposal-id>` | One proposal with its changes |
| `/inbox/routines` | Routines: prompts your agents run on a schedule |

Unknown paths open Home. A link to a note or file you cannot read (or that is missing or in the Bin) falls back to the list with a message. On phones, Back steps from the editor or preview to the list, then to the folders, then to Home, without leaving the site; in Tasks it steps from a card to its board, to the board list, then to Home. With a dialog or sheet open, Back only closes it.

**The bell.** Each notification opens what it is about and marks itself read: an event for a reminder; the proposal itself when a key or routine suggested one change (several open the Inbox); your item when an admin removed or lowered someone's access to it; **Settings → My access** when your own access, groups, or calendar feed links changed; **Inbox → Routines** when an admin paused a routine of yours; **Settings → API keys** for a key notice; **Settings → Security** for a new sign-in or a Google sign-in change; the vault, chat, agent, or knowledge base that was shared with you (a shared chat or agent opens the notifications list while your role cannot chat). Links carry ids only, never titles. While you can no longer open the item, the notice opens the app's list instead, and a link opened later shows that app's usual "not found" message. On a phone, Back returns to the notifications list (or the page you opened the bell from). Push notifications open the same places.

**Dropdowns.** Choices such as a calendar, a colour, a field type, or a sort field open a list under the control on desktop and a sheet from the bottom on phones. Type the first letters to jump to a choice, use the arrow keys, Home, and End to move, Enter or Space to choose, and Escape to close without choosing; long lists have a search box. On phones, Back closes the sheet and leaves the page and any dialog under it as they were.

## Today

Home shows what needs you today, in sections of up to ten items each, in three groups: **Today** (Due soon, Upcoming, My tasks, Proposals awaiting you), **Recent work** (Recent notes, Recent files, Recently edited rows), and **Housekeeping** (drafts, Leaving the Bin soon, Storage). Wide screens show one group per column, medium screens two columns with Housekeeping below, and phones one column. A section with items shows its count ("Due soon · 3"); an empty one folds into a single line, and a group with nothing in it says **All clear**. Every item is a link; Back from it returns to Today. **View all** opens the owning app.

| Section | Shows |
| --- | --- |
| Due soon | Cards due within seven days, or overdue, on boards you can open, except in done columns. A card with a due time shows it in your time zone ("Due today at 17:00") and counts as overdue once that time has passed |
| My tasks | Open cards assigned to you or added by you |
| Recent notes | Notes you can read, newest change first (someone else's note appears once it is published, with its published title) |
| Unpublished drafts | Your notes whose draft differs from what is published |
| Proposals awaiting you | Changes your MCP keys suggested that wait for you in the Inbox, including note drafts they wrote (this replaces Drafts from agents; if you had hidden that section, this one stays hidden) |
| Recent files | Files you can see in Files |
| Recently edited rows | Rows in collections you can open, most recently changed first (titles only) |
| Leaving the Bin soon | Your Bin items that are deleted forever within three days |
| Upcoming | Events on your calendars over the next seven days |
| Storage | How much of your storage quota is used, and how much of it is in the Bin |

**Refresh** reloads everything; coming back to the tab after a minute reloads too. If one section fails, it shows **Retry** and the others still load. **Customize** shows or hides sections; the choice is kept in this browser for your account only.

## Sharing and access

Everything starts private. To share a note, folder, file, board, task view, collection, or calendar, use its **Share** button: it opens the **Access sheet** (a side panel on a computer, a full-screen sheet on a phone; Back or Escape closes it).

- **Who can open this.** **Only me**; **People and groups I choose**; or **Everyone signed in** (everyone on this Nook except guests, never public). Notes and files can also **Use folder access**: they follow their folder's sharing, which never reaches subfolders.
- **People and groups.** Type in **Add people or groups…** and pick: groups come first with their size ("6 people · includes 2 guests"), then people with their team role. Each one gets a level from the menu next to it; the default is what sharing meant before (Can edit on boards, Can view elsewhere).
- **Your API keys.** As the owner you also see how many of your API keys can reach the item right now, counting keys given the item itself and keys given its folder (a folder covers the notes and files directly in it).
- **Levels.** Each person or group gets one of the levels the item offers:

| Item | Can view | Can comment | Can edit | Manager |
| --- | --- | --- | --- | --- |
| Notes and folders | Read the published note | — | Write the draft and publish a new version (never share, move, restore, or delete) | — |
| Files, task views | Open and download | — | — | — |
| Boards | Read cards and comments | Also comment and react | Also add, change, move, and bin cards, and add tags | Also rename the board, change its structure, columns, WIP limits, tags, and sprints, and share it up to Can edit |
| Collections | Read rows and export | — | Also add, change, undo, and delete rows | Also rename, change fields and saved views, and share up to Can edit |
| Calendars | See events | — | Also add and change events | Also rename, recolour, and share up to Can edit |

  **Everyone signed in** has its own level on boards, collections, and calendars (the menu next to that choice). Someone who gets two levels (directly and through a group, or through everyone) gets the higher one. Their **team role still caps it**: a viewer or guest only ever reads, and the sheet shows "Viewer role reads only" next to them.
- **Managers** see the same sheet without the "Who can open this" choice: they add and change people and groups up to Can edit, and cannot change other managers or their own access (their own row says **Ask the owner to change your access**). Only the owner changes who can open the item, makes managers, or deletes it.
- **Groups.** Admins decide who is in a group (Team → Groups); the sheet says so under each group, and notes when an admin added themselves. Sharing with a group reaches its members as they change: someone added later gets access, someone removed loses it at once.
- **Integrations.** An integration is an AI client or script your admins set up (Team → Integrations). It shows in **Add people or groups…** under **Integrations**, with a robot icon and an **Integration** badge, and you share with it like with a person, at a level. It never signs in: it reaches only what you share with it by name here (never what is open to **Everyone signed in**, and never through a group), and only through keys the admins hold, so **admins can read what you share with it**; its row and its picker entry say so. What it writes shows its name with the badge.
- **Saving.** **Save** applies everything at once. If someone else changed the access while you had the sheet open, Nook shows their version instead of overwriting it; make your change again.
- **Guests.** An admin can turn **sharing with guests** off in Team → Policies. Then guests are left out of the list, groups that include guests cannot be chosen, and saving a share that would reach a guest is refused. In Team → Groups, a guest cannot be added to a group that already has items shared with it, and someone in such a group cannot be made a guest (remove them from the group first). The switch is not retroactive: shares with guests made before it was turned off, and guests already in groups, stay until they are removed.

## Notes

Notes are Markdown documents organised in folders. Edits begin as drafts that save automatically; **Publish** records an immutable version that can be compared with others or restored. Notes start private; share a note or a whole folder from the [Access sheet](#sharing-and-access). A note's own sharing takes precedence over its folder's. People at **Can edit** on a note (or its folder) write its draft and publish new versions under their own name; only the owner shares, moves, restores versions, or deletes it. To move a note, drag it onto a folder, or use **Move to folder…** in the note's toolbar (in its ⋯ menu on a phone).

### Editor

Type `/` for the command menu. Besides headings, lists, checklists, quotes, and code blocks:

- **`/image`**, or paste or drop an image into the editor, uploads it to the note's folder in Files and embeds it. Only PNG, JPEG, GIF, and WebP are accepted, and the server's own type check must agree. Removing an image from a note leaves the file in Files.
- **`/whiteboard`** shows a whiteboard as a card in the note (thumbnail, name, **Open**): pick one of your boards or name a new one. Pasting a board's link alone on a line (⋯ → **Copy link for a note** on the board) does the same. The card follows the board's own sharing: people who cannot open the board see "Whiteboard unavailable" and not its name. The note itself stores only a link to the board, never its name, so Version history and agents reading the note do not show it either. If you moved the board to the Bin, your card says **In the Bin** with **Open Bin** (Settings → Bin). **Open** goes to the board; Back returns to the note.
- **`/table`** inserts a 3×3 table with a header row. A floating toolbar adds or removes rows and columns and deletes the table; tables are saved as GitHub-flavoured Markdown pipe tables and scroll sideways on phones.
- **Download as PDF** (editor toolbar, or the actions menu on phones) opens the browser's print dialog with a print layout of the note; choose "Save as PDF".

**Limitation:** an embedded image follows the sharing of the **folder** it was uploaded to, not the note's own sharing. If you share a note more widely than its folder, those readers see the text but a broken image. Nothing leaks; share the folder (or the image file) too if they need the images.

### Search

The search box at the top of the note list searches the text of your notes, not just their titles. Press `Ctrl+K` (`⌘K` on a Mac) or `/` to jump to it, and `Esc` to clear it.

- **What matches.** Every word you type must appear in the note, in any order; case and accents are ignored, so `creme` finds "Crème". The last word matches as a prefix while you type (`brul` finds "brûlée"); end the query with a space to match whole words only. Put words in `"double quotes"` to match them as an exact phrase. Punctuation and operators such as `AND`, `OR`, `NOT`, `*`, or `title:` are treated as ordinary text, not search syntax. Link text, image descriptions, and code are searched; link addresses are not.
- **What you see.** Your own notes are searched as you last saved them, including unpublished drafts, which are marked **Draft**. Notes shared with you are searched as their latest published version; you never see someone else's draft. Notes in the Bin are not searched until restored. Matches in the title rank first, and each result shows a highlighted excerpt, its folder, its owner when it is not yours, and when it was last edited.
- **Scope.** Search covers the section you are in: All notes, Shared with me, or one folder. Choose **Search all notes** to widen it. Opening a result from outside the current section switches to All notes.
- **Keyboard and phone.** Use ↑ and ↓ to move through results and Enter to open one. On phones, Back from a note returns to the results with your query kept; Back again closes the search. The query is kept in the browser tab's history state, never in the URL.
- **Limits.** 20 searches per 10 seconds per user; the list falls back to title matches and says so if you go faster. Queries are limited to 200 characters. Files are not searched yet.
- **Whiteboards.** While a search is showing, the **Notes** and **Whiteboards** chips switch what is searched. Whiteboards finds boards you can open by their name and the text on them, shows the matched text, and opens the board; Back returns to the search. The chip is hidden when Whiteboards is turned off in Settings → Modules.

## Files

Files lists documents in the same folders as your notes. Each app shows only its own item type. The file list header holds the file count, the List / Grid toggle, sort, the notification bell, and **Upload** (hidden for viewers and guests); Settings and Sign out are in the sidebar footer, as in Notes. The Bin is in Settings → Bin.

- **Upload** with the Upload button, by dropping files from your computer onto the list, or on phones from the upload sheet. Uploads run two at a time with a progress bar, and can be cancelled or retried. Each file may be up to `MAX_UPLOAD_BYTES` (100 MiB by default) and counts towards `USER_STORAGE_QUOTA_BYTES` (see [OPERATIONS.md](OPERATIONS.md#configuration)).
- **List and grid views.** The List / Grid toggle next to sort switches between rows and responsive tiles with image thumbnails and type icons. The choice is remembered per user in this browser. Sort by name, date, or size, and filter by name.
- **Preview.** On desktop the list takes the full width until a file is selected; the preview then opens as a pane on the right. Close (×) or `Esc` in the pane deselects the file. On phones the preview is its own screen.
- **Any file type is stored**, but only safe types are shown in the app. The server decides the type from the file's first bytes, not from its name or the browser's claim:

  | Type | Preview |
  | --- | --- |
  | PNG, JPEG, GIF, WebP | shown inline |
  | PDF | opens in a new browser tab |
  | UTF-8 text (`.txt`, `.md`, `.csv`, `.tsv`, `.log`, `.json`) | first 1 MiB shown as plain text, with a notice when truncated |
  | MP3, Ogg, WAV, M4A, MP4, WebM | audio or video player |
  | everything else (including SVG, HTML, Office files, archives) | download only |

- **Actions.** **Download**, **Rename**, **Move**, **Share**, and **Delete** are in each item's ⋯ menu (an action sheet on phones). Drag a file onto a folder to move it; the toast states the new effective sharing.
- **Keyboard.** ↑/↓ move the selection (←/→ too in the grid), Enter opens the preview, F2 renames, and Delete or Backspace deletes your own files.
- **Sharing** works like notes ([Access sheet](#sharing-and-access)): a file inherits its folder's sharing unless you give it its own. People you share with can preview and download but not change anything.
- **Delete** moves the file to the Bin; the toast offers **Undo** for a few seconds. When the file is attached somewhere, the confirm says where first ("Used on 2 cards and 1 event"); those places show "File removed" until you restore it.

### Attachments

Files you attach to something (an event, a card, a note, a chat message, a row; modules gain this one by one) are ordinary files kept in your own **Attachments** folder, marked with a lock in the Files sidebar. Nook creates it the first time you attach something.

- **Who can open an attachment:** you, plus anyone who can open the item it is attached to, for as long as they can. Unsharing the item, moving it to the Bin, or removing the attachment ends their access at once. Attachments never show up in other people's Files lists or search.
- **The folder is managed by Nook:** it cannot be shared, renamed, moved, or deleted, and nothing can be uploaded, created, or moved into it. You can rename its files, give one file its own sharing, download them, delete them, or **move them out** to keep them as ordinary files (they then stay when you remove them from the item).
- **Storage:** attachments count toward your quota once, however many items show them. When you remove an attachment from the last item that uses it, it moves to your Bin (restorable for 30 days). Uploads you never attached go to the Bin after a day.
- **The attach sheet** offers **Take photo** (phones and tablets: the camera opens directly), **Choose files**, and **From Files**, which lists only your own files. Picking a file from Files asks first, because everyone who can open the item will be able to open that file; it stays where it is in Files. On a phone the sheet slides up from the bottom, and Back closes it.
- **Photo location:** when you attach a JPEG through the attach sheet (or by pasting or dropping it), Nook removes the GPS position and other camera metadata in your browser before uploading, keeping only the picture's orientation.

Uploads through the Files app, MCP, or the REST API are stored exactly as sent: Nook does **not** strip EXIF or other embedded metadata (for example GPS location or author) from those images or from PDFs. Remove it before uploading if you plan to share the file.

## Tasks

Tasks holds kanban boards. **New board** asks for a name and a template: **Simple kanban** (To do, Doing, Done; the default), **Personal to-do**, **Task checklist**, **Scrum sprint board**, **Epic › Story › Subtask**, **Bug triage** (with Bug and Regression tags), or **Content pipeline**. A template only sets the columns and levels (and, for the Scrum sprint board, a first sprint); it adds no cards, and everything can be changed later in Board settings. Boards start private; share one with selected accounts or with everyone signed in.

- **Who can do what.** It depends on each person's level ([Access sheet](#sharing-and-access)). **Can edit** (what everyone you shared a board with had before, and still the default) adds, edits, moves, and comments on cards, attaches their own files, and moves cards to the Bin; **Can comment** only comments and reacts; **Can view** only reads. A **Manager** also renames the board and changes its structure, columns, WIP limits, tags, and sprints, and shares it up to Can edit. Only the owner deletes the board, changes who can open it, and deletes items forever. Shared boards show their owner's name.
- **Cards.** **Add a card** at the bottom of a column, or **New card** in the board's header, opens the new-card form (full screen on phones). Type the title, then optionally choose the column, a due date and time, assignees, a description, relations to other cards, and attachments; files upload as you add them. **Create** (or Enter in the title, or `Ctrl`/`⌘`+`Enter` anywhere in the form) adds the card and closes the form, **Create and open** opens the new card, and **Create another** (also `Ctrl`/`⌘`+`Shift`+`Enter`) keeps the form open in the same column for the next one. Everything is saved in one step, so a refused card (a full column, or a linked card that is no longer available) saves nothing, and the reason shows next to the field. Close, Escape, or Back with anything entered asks "Discard this card?" first; discarding moves the files you uploaded to your Bin. Drag cards within or between columns on desktop. Every card's ⋯ button opens **Move to…**, which lists the columns and Top or Bottom; with a card focused, `Alt` plus an arrow key moves it up, down, or to the next column. If someone else changed the column meanwhile, the card jumps back and the board reloads.
- **The card view.** Click a card (or press Enter on it) to open it; it has its own URL, and Back closes it. On desktop it opens as a full-height panel on the right: the title and actions stay at the top, the fields scroll on their own on the left of a wide screen, and the comment box stays at the bottom while the comments scroll above it; click the dimmed board, Escape, or ✕ to close it. The title saves when you leave the field. The description is Markdown, edited with **Edit** and saved with **Save**; if someone else saved first, choose **Reload** (take theirs) or **Copy my text**. Comments load 50 at a time; you can edit or delete your own, and the board owner can delete any. On a wide screen, **Open as page** (the expand icon next to Move and Delete) shows the card as a full page with its own URL, with the description and comments on the left and the fields and relations on the right; **Collapse** or Back returns to the card over the board, and the board's name at the top goes back to the board. A link to the page opens it directly, on phones too (there the card is already full screen, so the expand icon is hidden).
- **Reactions.** Under each comment, tap an emoji chip to add or remove your reaction; it shows how many people reacted and is highlighted when you did (hover it, or open the picker on a phone, to see who). **Add reaction** (the smiley) offers 12 emoji: 👍 👎 ❤️ 😂 🎉 👀 🚀 ✅ 🔥 🤔 🙏 😢. On a phone it opens as a sheet that also lists who reacted; Back closes it. Anyone who can comment can react; viewers and guests see reactions but cannot add them. Reactions send no notifications and do not count as editing the card, and deleting a comment removes its reactions.
- **Who wrote it.** Each comment shows its author's picture, or their initials when they have none, the same as everywhere else in Nook.
- **Attachments.** **Attach** adds files to the card, and the comment box can attach files to a comment. Images pasted or dropped into the description become attachments and show inline. Attachments never appear in Files; they are readable by the people who can open the board, and only while the card and your access last. Removing an attachment from its last card moves it to your Bin.
- **Phones.** A board shows one column at a time: swipe sideways, or tap a column in the strip above it, which also shows how many cards each column holds. Back returns to the same column.
- **Due dates and assignees.** The card view has **Due** (a date; **Clear** removes it). After a date, **Add time** sets an optional time in your time zone (**Remove time** takes it off); moving the date keeps the time. Someone in another zone sees it as, for example, "17:00 Europe/Berlin (11:00 your time)", and on the board and in Today at their own local time. **Assignees** takes up to 20 people: type part of a name to search everyone who can open the board, and remove someone with the ✕ on their chip. People picked while the list is open are saved when it closes. Someone who has lost access to the board shows "(no access)" and can only be removed. Cards show a due chip (with the time when there is one): red when overdue, amber for today and the next days, and up to three assignees as initials with "+N" for the rest. The board owner sets each column's **State** from its ⋯ menu: **To do**, **In progress**, or **Done** (a new board's columns start as one of each, and a new column is In progress). Cards in a Done column count as finished and are left out of Today; the states are also what **State** filters, My work, and views use across boards.
- **Tags and flags.** **Tags** in the card view takes up to 10 of the board's tags: type to filter them, or type a new name and choose **Create “…”** (anyone who can open the board can add a tag). Tags picked while the list is open are saved when it closes; the ✕ on a chip removes one at once. Each board has up to 100 tags with names of up to 40 characters, and each tag has a colour. The board owner also sees **Manage tags…**, which renames a tag (Enter or leaving the field saves), changes its colour, or deletes it; deleting removes it from every card on the board and cannot be undone. **Flags** are four fixed toggles, **Urgent**, **Blocked**, **Needs review**, and **On hold**; each press saves. **Blocked** is a flag you set yourself, separate from cards this one depends on. On a phone the tag list is a bottom sheet and **Manage tags** is full screen; Back closes them.
- **What a card shows on the board.** From the top: its flags as icons (urgent red, blocked amber, needs review blue, on hold grey), the title (two lines), the start of the description (two lines, one on a phone), then the due chip, up to three tags with "+N", the comment, attachment, and related-card counts (an amber count when cards it depends on are still open), and up to three assignees' initials. A card with many of these wraps them onto a second line rather than hiding any. Screen readers hear it all as one sentence, for example "Fix login, urgent, due tomorrow at 17:00, tags Backend, assigned to Asha and Ben".
- **WIP limits.** The board owner can cap how many cards a column holds with **Set WIP limit…** in its ⋯ menu (1 to 1000; **Remove limit** takes it off). The column header then shows "3 / 5", amber when full and red when over (a limit can be set below the current count; the cards stay). A full column takes no new cards: adding one or moving one in from another column is refused with a message, a dragged card cannot be dropped there, and **Move to…** lists it as full. Reordering within the column and moving cards out always work, and a card restored from the Bin always returns. Everyone who can open the board sees the limit; only the owner changes it.
- **Relations.** The card view's **Relations** links a card to others on any board you can open: choose **Depends on**, **Needed by**, **Relates to**, **Duplicates**, or **Duplicated by**, then type part of the other card's title. Links are grouped by type; click one to open that card (Back returns). Two cards have at most one link, whatever its type. When a card depends on open cards, the section reads "Blocked by N open cards". Someone who cannot open the other board sees "Restricted card" instead of its title, and can still remove the link. Linking or unlinking never counts as editing either card, so it never interrupts someone editing it.
- **Views.** The icons at the top of a board switch between **Columns** (the lanes), **Table**, **List**, and **Calendar**. The table sorts by any column header (click again for descending, a third time for the board order) and scrolls sideways on a phone with the title column kept in view. The list groups cards by column, assignee, tag, flag, or due date (**Group by**); a card with two assignees or tags appears in each group, marked "also in …", and each group folds away with its heading. The view, grouping, and sort are part of the page address, so a reload or a shared link opens the same view; Back returns to the previous view, and opening and closing a card keeps it. Drag and drop works in Columns; in the other views each card's ⋯ (**More actions**) opens **Move to…**. That sheet, in every view, also has **Copy link**, which copies the card's link without the view or filters; the open card has the same **Copy link** button in its header.
- **Board calendar.** The **Calendar** view shows this board's cards on a month grid (or an **Agenda** list) by due date; a card with a time sits on your local day and time. It shows due dates only: events linked to cards stay in the Calendar app. Cards without a due date wait in **Unscheduled**. On a computer, drag a card to another day to move its date (its time and time zone stay as they were), or onto **Unscheduled** to remove the date; with a card focused, `Alt` plus ← or → moves it a day and ↑ or ↓ a week. Every card in a day list or in Unscheduled also has **Set due date…**, which is how you move cards on a phone (there, **Unscheduled (N)** opens the list). If someone else changed the card meanwhile, it moves back and the board reloads. Filters apply here too; paging months does not add Back steps, and WIP limits do not apply to date changes.
- **Filters.** Under the board's name, **+ Filter** adds a filter: pick a field (Assignee, Tag, Flag, Due, Column, or Relations), then one or more values; a card matches any value of a field and every field. Due takes Overdue, Today, the next 7 days, the 7 days after, No date, or a date with Before, On, or After. "Next 7 days" is today plus the 6 days after it; "the 7 days after" are the 7 days that follow. Each filter shows as a chip: click it to change it, or its ✕ to remove it; **Clear** removes them all. The **Filter cards** box matches the title and description preview, ignoring case and accents. Filters apply in every view and are part of the page address, so a reload or a link shows the same cards to anyone who can open the board. Changing a filter does not add a Back step. The board's lanes keep their full counts for WIP limits while filtered.
- **Tasks home.** The top of Tasks has three segments, **Boards**, **My work**, and **Views**; each has its own address (`/tasks`, `/tasks/my`, `/tasks/views`), so Back returns to the previous segment and a reload keeps it.
- **My work.** Every card assigned to you on any board you can open, open ones by default, grouped by due date (Overdue, Today, This week, Later, No due date). The chips above the list pick **Open**, **To do**, **In progress**, **Done**, or **All**; **+ Filter** adds Board, Tag, Flag, Due, Sprint (current, next, or the backlog on each board), Parent (none), Level, or Relations (including Has subtasks), and **Find cards** matches titles. "Assignee is Me" is always on. The icons switch between the list, a **Table**, and **Columns** (one lane per state); **Group** and **Sort** change the list. Results load 50 at a time: **Load more** fetches the next ones. Each card's ⋯ opens **Move to…** with that card's board columns (there is no dragging between boards or lanes). Opening a card shows it over its board; closing it, or Back, returns to My work as you left it. Today's **My tasks** section links here with **View all**. Once you change the filters, **Save as view** keeps them.
- **Views.** A view is a saved filter and layout across your boards, such as "Urgent cards on Web and Home". The Views segment lists **My views**, views **Shared with me**, and views shared with **Everyone**. **New view** opens an empty view: add at least one filter other than text (a board, a person, a state, a tag, a flag, or a due date) before it shows cards, then **Save view**. Changing a saved view's filters, layout, grouping, or sort shows **Unsaved changes**: **Save** keeps them, the undo icon drops them, and the ⋯ menu has **Save as a new view…**, **Rename**, **Duplicate**, **Share…**, and **Delete view** (with Undo, which brings it back as a private view). If the view was changed elsewhere since you opened it, Save offers to reload the latest version. Sharing works as for boards (**Private**, **Selected people**, **Everyone here**). A view never widens access: everyone who opens it sees only cards on boards they can open themselves, and a board they cannot open shows as "Restricted board". People you share with see the view read only and can **Duplicate** it into a private copy of their own. Up to 50 views per person.
- **Board settings.** The gear in a board's header opens **Board settings** (a full-height sheet on phones; Back closes it): the name (**Rename**), the **Structure**, a per-person **Display** option, **Add column**, **Share board…**, and **Move board to the Bin**. Everyone sees the structure; the owner and managers change it, and only the owner moves the board to the Bin.
- **Structure: tasks with subtasks, epics and stories.** A board starts flat (every card is a card). In Board settings the owner picks **Task › Subtask**, **Sprint › Task**, **Sprint › Task › Subtask**, **Epic › Story › Subtask**, or types their own names for up to three levels, and chooses which level **New cards are created as** (the level the columns show). "Sprint ›" turns on sprint planning (below). Removing a level is refused while any card (even one in the Bin) is at that level, with a message saying how many.
- **Subtasks.** On a board with levels, a card shows its children as a checklist named after the level below (**Subtasks**, or **Stories** on an epic) with a count like 2/5 and a progress bar. **Add subtask…** at the bottom adds one on Enter and stays ready for the next; **Add with details** opens the new-card form with the parent filled in. Ticking a subtask moves it to the board's first done column, and unticking moves it back to the first open column; when the last one is done, a message offers to move the parent to done too (nothing moves by itself). Each row opens its card; ✕ takes a story out of its epic, and on a subtask **Make it a task** lifts it out instead. A board without a done column shows each subtask's column instead of a tick box.
- **Parents.** A card below the top level has a parent field named after the level above (**Epic**, **Story**, or **Task**): type to find a card one level up on the same board ("Choose an epic…" when it has none); a story can leave its epic, but a subtask always needs its task: removing it asks for another one or offers **Make it a task**, and one restored without its parent says "Detached subtask" with both choices. **Level** changes what a card is (a story becomes a subtask, say) while it has no children. The card view shows its parents above the title; tap one to open it, and Back returns. On the board, a card shows its parent as a small chip (tap to open it) and its subtask count, for example 2/5. To give a card a parent on a computer, drag it onto a card one level up ("Make subtask of …"); on a phone, its ⋯ → **Set epic…** (or task, story) lists the candidates.
- **What the columns show.** Columns show the level new cards are created at. Subtasks sit inside their parent, and epics show as the chip on their stories; **Show all levels on the board** in Board settings (just for you, on this device) puts every card in the columns. Loose cards without a parent always show. With a filter on, every matching card shows, whatever its level. In **Table**, cards form a tree (children under their parent, with ▸ to fold them away) with Level and Parent columns while the table is unsorted; **List** can group by **Parent**; and the filter bar adds **Level** and **Parent**, and **Has subtasks** under Relations.
- **Sprints.** On a board that plans in sprints (the **Scrum sprint board** template starts with a planned **Sprint 1** of two weeks), a sprint switcher sits under the board's name: the active sprint (the default), planned sprints, **Backlog** (cards in no sprint), **All cards**, and recently completed sprints. The board, table, list, and calendar then show only that sprint's cards, with a strip such as "4 days left · 26 Sept – 9 Oct · 8 of 14 done" and a bar of done, in-progress, and to-do cards (counts only, no points). The choice is part of the page address, so a reload or a link opens the same sprint, opening a card keeps it, and Back returns to the sprint you had before. New cards start in the sprint on screen. A card's **Sprint** field moves it to another sprint or the backlog; subtasks follow their task and show its sprint read-only. Only the board owner manages sprints.
  - **Creating a sprint.** The last entries of the sprint switcher are **＋ New sprint…** (owner) and **Manage sprints…**. New sprint opens a small dialog (a bottom sheet on phones): the **Name** (the next one, such as "Sprint 2"), the **Starts** date, and a **Duration** of 1, 2, 3, or 4 weeks or **Custom** (which shows the end date to pick). The end date follows the start and the duration. **Create** adds it as planned; **Create and start** (when no sprint is active) starts it at once. Back or Escape closes the dialog. When no sprint is running, the strip says **No active sprint** and gives the owner **Start Sprint 1** (the next planned sprint) and **New sprint**; everyone else sees the words only.
  - **Sprint defaults.** **Board settings → Sprint defaults** (owner) sets what a new sprint starts with on this board: the **Default duration** (1–4 weeks, or Custom from 1 to 60 days), **Start on** (the day after the previous sprint ends, a chosen weekday on or after that, or today), and an optional **Name pattern** such as `Sprint {n}`, where `{n}` counts up from the board's highest number (left empty, new sprints follow the latest sprint's name). **Save defaults** keeps them with the board, for every device. The Scrum sprint board starts with two weeks, the day after the previous sprint, and `Sprint {n}`; older boards without defaults suggest a sprint as long as the latest one. Members see the defaults in words.
  - **The Sprints sheet.** **Manage sprints…** (in the switcher, and in Sprint defaults) opens the board's sprints in their own sheet, with its own address (`/tasks/<board-id>/sprints`), so Back returns to the board. It lists the planned and active sprints and the completed ones (**Show older** pages further back). The owner adds one there too (**New sprint**, the same form), renames or re-dates a sprint, starts a planned one (one active at a time), deletes an empty planned one, and **Complete…** the active one (also on the strip). Completing asks where the unfinished cards go (the next planned sprint, another planned one, the backlog, or a new sprint named and dated by the sprint defaults); done cards stay in the completed sprint, and a message offers **View** to follow the rest. Back or Escape closes the dialog without completing, and the sheet stays.
  - The filter bar also has **Sprint**.
- **Moving a tree to the Bin.** Moving a card to the Bin also moves the cards under it, and the Bin shows one item with "+ N subitems". **Undo** or **Restore** brings them all back in their columns. A subtask you binned on its own before keeps its own Bin entry; restoring it while its parent is still in the Bin brings it back without a parent.
- **Limits.** 50 boards per owner, 20 columns and 1000 cards per board, three levels and 100 direct subtasks per card, 500 comments and 50 attachments per card, 10 attachments per comment.

## Collections

Collections are typed tables for anything you track: a home inventory, subscriptions, expenses, recipes, contacts. Open them from the **Collections** link on Today, or at `/collections`. The Collections page lists your collections and those shared with you; on your own, the buttons next to the name **Rename**, **Share**, or **Move to Bin** it, as on the Tasks board list.

- **New collection.** Start blank (a Name and a Notes field) or from a template: Home inventory, Subscriptions, Expenses, Recipes, or Contacts. A template is copied, so changing your collection never changes the template. **Create and import CSV** starts the import right away.
- **Fields.** The owner edits fields with **Fields**: up to 50, each a text, number (with decimals and a unit), date, checkbox, select, multi-select, link (`http` or `https`), note, or files field. The first field is the row's title everywhere and is always text. Fields can be renamed, reordered, made required, and given options with colours. A text field can become a link and back, and a select can become a multi-select; other type changes are refused. Removing a field hides its values at once; each row drops them the next time it changes.
- **Rows.** On desktop, edit cells in place: a change saves when you leave the cell (Enter saves, Escape reverts). Multi-line text, notes, and files open the row. On phones the list shows each row's title and up to three more values; tap a row for a full-screen editor. If someone else changed the row since you loaded it, your edit is not saved and the row offers **Reload**. Up to 10,000 rows per collection.
- **Undo.** Each row keeps its previous values. **⋯ → Undo last change** restores them once (fields removed since stay removed). The same menu has **Copy link** and **Move to Bin**.
- **Find, sort, and filter.** **Find rows** matches text and link fields. **Sort & filter** sorts by up to 3 fields (empty values last) and filters by up to 10 conditions that must all match, and chooses which fields are shown.
- **Saved views.** The owner can **Save as view** from the sort and filter sheet. Views appear as chips above the rows (up to 20), have their own URL, and can be updated, renamed, or deleted by the owner. Everyone with access can use them.
- **Sharing.** The owner shares a collection from the [Access sheet](#sharing-and-access), each person or group at **Can view** (read and export), **Can edit** (add, change, undo, and delete rows, attach files), or **Manager** (also rename it, change its fields and saved views, and share it up to Can edit). Only the owner deletes the collection. People who can only view see "View only".
- **Notes in rows.** A note field links a note you can read. Linking never shares the note: people who cannot read it see "Restricted note", never its title.
- **Attachments.** In a files field, **Attach files** uploads files for the row (up to 20 per row). They count towards your storage quota but never appear in Files; they are readable by everyone who can open the row, and nobody else. Removing a file from its last row moves it to the uploader's Bin; an upload that was never attached is binned after a day.
- **Search.** The search box on the Collections page finds rows in every collection you can open, by title, text, links, numbers, dates, and option labels (not note titles or file names). Back from a result returns to the results.
- **CSV import.** **Import CSV** takes a file up to 2 MB with a header row and up to 5000 rows of up to 50 columns. Columns are matched to fields by name, and you can remap or skip them. **Check** lists every problem first; the import adds all rows or none. Options match by label (several separated by `;`), and checkboxes accept yes/no, true/false, or 1/0.
- **CSV export.** **Export CSV** downloads the rows and fields of the current view as UTF-8 for spreadsheets. Text that a spreadsheet would run as a formula (starting with `=`, `+`, `-`, `@`, or a tab) is prefixed with `'`; importing the file again removes it.
- **Bin.** Deleted rows and collections go to the Bin for 30 days. A row is listed for the collection owner and for whoever deleted it; either can restore it while they can still edit the collection, but only the owner deletes it forever. A row whose collection is itself in the Bin can be restored only after the collection.

## Calendar

Calendar (`/calendar`) shows your calendars and the ones shared with you as an **Agenda** (the next 60 days) or a **Month** grid (`/calendar/month/<yyyy-mm>`). Opening an event gives it its own address (`/calendar/event/<id>`), and Back returns to where you were.

- **Calendars.** **Calendars** lists them with their colours, lets you hide some from view, creates new ones, and shares one from the [Access sheet](#sharing-and-access), each person or group at **Can view** (see events), **Can edit** (add, change, and remove events), or **Manager** (also rename, recolour, and share it up to Can edit). Only the owner deletes a calendar. Viewers and guests always only view.
- **Events.** **New event** takes a title, a time with a time zone (or **All day**), a location, a description, and **Repeat** (daily, weekly on chosen days, monthly, or yearly, ending never, on a date, or after a number of times). A repeating event's **Skip <date>** leaves one date out. **Link a note** attaches what the event needs, such as an agenda or a packing list; a linked note, card, or row shows as restricted to people who cannot open it. **Undo last change** puts back the previous values once.
- **Attachments.** An event can carry up to 20 files, such as the agenda, slides, or tickets.
  - **Adding files.** If you can edit the event, open it and choose **Attach files**: **Take photo** (on a phone), **Choose files**, or **From Files** to pick one of your own files. You can also drop files on the Attachments section.
  - **In the event sheet.** In **New event** or **Edit event**, the Attachments field takes the same choices, and you can also paste a screenshot or drop files anywhere on the sheet. Files upload straight away but are attached only when you save. **Cancel** or **Discard** leaves the event as it was and moves those uploads to the Bin.
  - **Who sees them.** Everyone who can see the event can open and download its files. Tap a file to preview it; Back closes the preview. Nobody else can open them, and people stop seeing them as soon as the calendar stops being shared with them or the event goes to the Bin.
  - **Storage.** Uploads go to your **Files › Attachments** folder and count toward your storage. Picking a file from elsewhere in Files asks first, because the event's readers will be able to open it; it stays in its folder.
  - **Repeating events.** A repeating event's files belong to the whole series, so every date shows them. Skipping a date or **Undo last change** does not change them.
  - **Removing files.** You can always remove a file you attached yourself. The calendar's owner and managers can remove anyone's. A removed upload that nothing else uses moves to its owner's Bin.
  - **Bin and feeds.** Restoring an event from the Bin brings its files back. Deleting the event forever moves its unused uploads to the Bin. Calendar feeds and email never include files, file names, or links to them, so a **Busy only** or **Full details** link reveals none.
- **New event on a day.** In the month grid, click an empty part of a day (or its **+**, shown on hover) to open **New event** for that day at 09:00, or the next full hour today; a day from the next or previous month pages there first. On a phone, tap the day to see its events, then **New event on <date>** below the grid. Back closes the sheet.
- **Tasks due.** Cards with a due date on boards you can open appear in the agenda and the month as **Tasks due** (they stay cards; change them in Tasks). Turn them off in **Calendars**.
- **Reminders.** Under **My reminders** on an event, **Add reminder** sets one for you only ("15 minutes before", "At the start", "9:00 the day before"). When it is due it appears under the bell and at `/notifications` (**Mark all read** clears the count).
- **Push.** On an HTTPS origin, **Settings → Notifications** turns on push for this device, lists your devices, and has **Send test**. A push carries no content: the device fetches the notification from Nook and shows the same line as the bell, with what kind it is underneath ("Calendar reminder", "Suggested changes in your Inbox", or "Sharing and access"). On `http://localhost` or a LAN address, reminders appear in the bell only.
- **Bin.** Deleting a calendar or an event moves it to the Bin for 30 days, like everything else.

### Calendar feeds

A feed link lets a phone or desktop calendar app (Apple Calendar, Google Calendar, Outlook, Thunderbird) subscribe to one of your Nook calendars, read-only. In Calendar, open **Calendars** and choose the subscribe button (the feed icon) next to a calendar; you can do this for your own calendars and for any calendar shared with you.

1. Choose what the feed shows. **Busy only** sends just the times, each titled "Busy", and names the calendar "Busy". **Full details** sends titles, places, and descriptions. Repeats and skipped dates are included either way.
2. **Create link**, then **Copy link** and paste it into your calendar app's "subscribe by URL" or "add calendar from the internet" option. The link is shown **only once**; Nook keeps only a fingerprint of it. If you lose it, create another.
3. The dialog lists your links for that calendar with when each was last used. Revoke (the bin icon) stops a link at once; the subscribed app simply stops updating.

Things to know:

- **Anyone with the link can read the feed** until you revoke it, without signing in and without your two-factor code. Treat it like a password; prefer **Busy only** when you share it or are unsure.
- **Cloud calendars fetch the feed from their own servers.** Google, Outlook, and iCloud (on the web) cannot reach an address that only works on your tailnet or home network; use a calendar app on the device itself, or a public HTTPS address.
- A link follows your access: if the calendar is moved to the Bin, or the owner stops sharing it with you, the link stops working (and works again if that is undone). Links you create are yours alone; other people's links are not shown to you.
- Up to 5 links per calendar per person, each fetched at most 60 times an hour (calendar apps typically refresh every 15 minutes to a few hours). At most 5000 events are sent. Timed events carry their time zone; the app shows them in yours.

## Whiteboards

Boards drawn with the Excalidraw editor at `/whiteboards`, each saved as a `.excalidraw` file in one of your folders. Drawing saves on its own; only the owner edits, and people it is shared with view.

- **Pictures.** The picture button in the bar (or the editor's image tool, or `9`) opens **Insert image**: pick one of your pictures or one shared with you, or **Upload a picture**, which saves it in Files in the board's folder. Dropping or pasting a picture file uploads it the same way. A picture joins the board once its file is saved; if you leave while it is still uploading, it is not added, and Nook says so. The board stores only a link to the file: people you share the board with see a picture only if they can open that file themselves (others see a placeholder), a deleted file leaves a placeholder, and pictures count toward your storage once, as files. Pictures uploaded from a board or brought in by an import go into the board's folder and take that folder's sharing, like pictures in a note. If a picture comes back (Undo, another tab) after its file was deleted or unshared, Nook takes it off the board, says so, and keeps saving. Thumbnails show no pictures. The editor draws in a dark theme by inverting the canvas colours, so pictures on a board look slightly shifted in colour there; the file itself and **Export PNG** keep the original colours.
- **Links.** Select a shape and use the link button in the bar (or ⋯ → **Link shape to a Nook item**) to link it to a note, file, whiteboard, task board, card, collection, or event. Opening the link goes there in Nook; Back returns to the board where you were. Web links (https) and email links typed into Excalidraw's own link box open in a new tab after Nook shows you the full address. Other kinds of links are not kept.
- **History.** ⋯ → **History** (owner only) lists the versions Nook kept: one when you empty a board or remove most of it, and one every 30 minutes while you draw, up to 20 per board (they count toward your storage; the half-hourly one is skipped, never your edit, when your storage has no room for it). Each shows its time, shape count, and a preview. **Restore** saves your latest changes first and then makes that version the current one, keeping what was there as a version too; **Save as copy** opens it as a new board.
- **Duplicate and import.** ⋯ → **Duplicate** makes a private copy you own ("Name (copy)", then "(copy 2)"…); people a board is shared with can duplicate it too, and pictures they cannot open are left out. **Import** on the list opens a `.excalidraw` file (at most 32 MB): its pictures are saved in Files next to it, and a drawing Nook cannot keep (embedded web pages, unsafe links, other kinds of pictures) is refused with the reason.
- **Export.** **Export PNG** includes the pictures you can see. ⋯ → **Export SVG** downloads an SVG file; it names Excalidraw's hand-drawn fonts instead of embedding them, so text looks different where those fonts are not installed.

## Bin

Deleting a note, a file, a card, a board, a collection, a row, a calendar, an event, or a vault, a vault environment, or a secret moves it to the shared **Bin** for exactly **30 days**. The Bin is a section of [Settings](#settings): **Settings → Bin**, under **Workspace** in the Settings nav, with a small count when it holds items, at `/settings/bin` (the old `/bin` still works and opens the same screen). On a phone it is one of the entries of the Settings list and opens as its own screen with a back arrow; a row's **⋯** opens its actions sheet, and Back closes the sheet before it leaves the Bin. The retention period is fixed. The Bin lists your own deleted items, newest first, with the days left for each; the chips filter by Notes, Files, Tasks (cards and boards), Collections (collections and their rows; see [Collections](#collections) for who sees a binned row), or Calendar (calendars and events). Viewers and guests cannot restore or empty the Bin; their items leave after 30 days.

- **Cards and boards.** A deleted board is listed for its owner. A deleted card is listed for the board's owner and for the person who deleted it (while they can still open the board); either can restore it, but only the owner can delete it forever. A restored card returns to the bottom of its column, or of the first column if its column was deleted. A card on a deleted board can be restored only after the board. Deleting a card or a board from Tasks offers **Undo** in the toast.
- **Attachments.** When a card or board is deleted forever, or a file is removed from the last card that used it, the file moves to its uploader's Bin, labelled as a card attachment. Restoring it puts it in Files, in your Default folder.

- **What is kept:** everything. A binned note keeps its draft, published versions, and files on disk; a binned file keeps its bytes. Sharing is kept too, so restoring an item gives its previous audience access again. While an item is in the Bin nobody can read it, including its owner outside the Bin and MCP clients.
- **Restore** puts an item back in its original folder, or in your Default folder if the original was deleted. The toast names the folder and says when the item is shared again (a Default folder shared with others widens its audience).
- **Blank notes** that were never published skip the Bin and are removed at once. Any note with content, published or not, goes to the Bin, including an unpublished note whose draft you discard.
- **Delete forever** and **Empty Bin** remove items permanently. After 30 days an hourly sweeper (which also runs at boot) deletes expired items for you.
- Files in the Bin still count towards your storage quota until they are deleted forever.

## Vault

The **Vault** keeps a team's secrets (API keys, database URLs, service passwords, certificates) with a value per environment: dev, staging, prod, or names you choose. **Encrypted at rest; anyone with the server and its key can read every secret.** It is a secrets manager for your own services, not a personal password manager: there is no browser extension or autofill (use Bitwarden or Vaultwarden for website passwords). Names, environment names, and tags are not encrypted, so put anything sensitive in a value or a comment. The Vault appears only when your admin has set the server's vault key; guests never see it.

- **Vaults.** **New vault** asks for a name, an optional description, and its environments (dev, staging, and prod to start; add, rename, or remove them). The list shows **Your vaults** and **Shared with me**. Admins get no access to a vault they are not in.
- **Who has access** (**Access** on a vault, `/vault/<vault-id>/access`; owners, and environment admins for their environments). Add people or groups, then give each a level per environment: **No access**, **Read** (see and copy), **Write** (also set, clear, and import), or **Admin** (also rename or delete that environment, and give others read or write there). **Owners** hold everything, on every environment, and a vault always keeps one. Team roles cap it: viewers can only read and cannot own a vault; guests and integrations are never offered. A group gives its members the same levels (the higher of their own row and the group wins; guests in a group still get nothing). **Save** applies the whole list; if someone else changed it meanwhile, the page shows the latest. People you add hear about it in the bell and by email (the vault's name only). Removing someone starts a new data key for the vault and reminds you that they may have copied values: rotate those credentials where they are issued; **Show what they read** opens their Activity. A member can **Leave vault** in the vault's settings.
- **Protected environments** (prod, to start; owners switch it per environment in the vault's settings). They ask for your password to *see* values, not to change them. Revealing, copying, showing an old version, or exporting a protected environment asks you to confirm it's you (your password, and a code when two-factor is on); that opens protected environments for 15 minutes on this device. Saving a value, **Also save in**, clearing, restoring an old version, importing, deleting a secret, and restoring it from the Bin need only your write access. Editing a protected value while you have not confirmed opens an empty **New value** field: type the new value and save. Leave **New comment** empty to keep the current comment. **Show** brings back the current value after you confirm it's you (if you already typed something, it asks before replacing it). Without the confirmation, an import preview into a protected environment does not compare with the current values, so a name that already has a value shows as replaced (or skipped) rather than unchanged. Lifting protection, and moving a protected environment to the Bin, still ask.
- **Secrets.** Each secret has a name, a type (**Value** for one string, **Login** for a username, password, and URL, **Note** for multi-line text), an optional encrypted comment, and tags. It can hold a different value in each environment.
- **On a computer** a vault is a grid: secrets are rows and environments are columns. A cell shows `••••••••` and its version, **Not set**, or a lock. Click a cell to **Reveal** (it hides again after 30 seconds, when you close the dialog, or when you switch tabs), **Copy** (the clipboard is cleared after 30 seconds while Nook has focus; clipboard managers may keep a copy), **Edit**, or **Clear**. Many environments scroll sideways inside the grid.
- **On a phone** choose the environment at the top (it stays in the URL), then each secret is a card with **Reveal** and **Copy**. Tap a name to see the secret with one card per environment; Back returns to the list with the same environment.
- **Editing** starts from the current value (opening it counts as a reveal). **Generate** makes a random value in your browser: characters (8–128, with the character sets you pick), a hex or base64url token (16–64 bytes), or a passphrase (3–12 words); it shows the strength in bits. **Also save in** writes the same value to other environments at once. If someone changed the value since you opened it, nothing is saved and you can load the latest.
- **History.** Every change, including a clear, is a new version; the last 20 per environment are kept. **History** on a cell or an environment card lists them with who wrote each; **Show** opens one (it hides again after 30 seconds) and **Restore** writes it back as a new version.
- **Import** reads a `.env`, JSON, or CSV file in your browser (it is never uploaded), then **Preview** shows what would be created, replaced, left unchanged, skipped, or refused, before **Import** writes it. Choose whether values that differ are kept or overwritten. **Export** downloads one environment as `.env`, JSON, or CSV, optionally with value comments: the file holds the values in plain text, so keep it private and delete it after use. Exports are recorded and limited to 10 an hour.
- **Activity** (`/vault/<vault-id>/activity`) lists who revealed, changed, imported, exported, or shared what, and when, filtered by person, kind, and environment. Owners see everyone's; members see their own. It never shows values. Something a vault key did shows the key as `key:<name>` with whose key it is; **API keys** filters to those events.
- **Vault keys** let scripts, CI jobs, and AI clients read and write secrets without a person signed in: see [Vault keys](#vault-keys) under Settings → API keys. A vault's **Access** page lists the **Keys with access** to it.
- **Tags** filter the list with the tag box next to Import and Export.
- **The data key.** Owners can **Rotate data key** in the vault's settings (it also happens when someone loses access): new values use the new key at once and older ones move to it in the background. It protects old backups; it cannot take back what someone already saw.
- **Storage.** The vaults you create can hold up to 64 MiB of encrypted values, history included (the list shows how much is used); clearing values or emptying deleted secrets from the Bin frees space.
- **Deleting** a secret, an environment (with its values), or a vault moves it to the Bin for 30 days (the **Vault** chip there). Owners see and restore everything of their vaults there; a member sees only what they deleted, while they can still write there. Only owners delete forever. Restoring a secret whose name was reused, or an environment whose short name was reused, asks you to rename the other one first. Deleting a vault forever destroys its key.
- Every reveal, copy, and change is recorded for the vault (never the value itself). Reads and changes are each limited to 300 per 10 minutes.

## Chat

**Chat** (`/chat`) is where you talk to **agents**: an agent is a prompt, a model, and a step limit that you make in **Settings → Agents**. Answers come from a **model provider an admin configured** in Settings → AI → Model providers: the one the agent's editor picks, or the default provider. So **every message you send, the agent's prompt, and every reply leave this Nook for that provider's endpoint**; the composer says so. Chat appears only once an admin has set the server's key and a provider; guests never see it, and an admin decides which roles may chat (admins, members, and viewers to start) and who may create agents (admins and members).

- **On a computer** the chats are on the left, grouped **Pinned**, **Today**, **Yesterday**, **Previous 7 days**, then by month, with a search box over titles and your messages; the chat is on the right. **On a phone** `/chat` is the list and a chat opens as a screen of its own with a back arrow (Back returns to the list, Forward reopens the chat).
- **New chat** asks for an agent (a dropdown; the agent's starter prompts are offered on the empty chat), then your first message names the chat. An agent is fixed per chat: pick another agent for another chat.
- **Writing.** <kbd>Enter</kbd> sends and <kbd>Shift</kbd>+<kbd>Enter</kbd> adds a line on a keyboard; on a phone Enter only adds a line and **Send** sends. While the agent answers, Send becomes **Stop**; stopping keeps what arrived. An answer keeps going when you leave the chat or the tab; the chat shows a dot in the list, and coming back resumes the stream where it was.
- **Replies** render Markdown as GitHub does: headings, bold, italic, strikethrough, lists (numbered lists keep their first number), task lists, quotes (nested too), tables with their column alignment (they scroll sideways inside the reply, never the page), code blocks with their language and **Copy**, horizontal rules, footnotes, and links. A single line break in a reply is a line break. Raw HTML in a reply shows as text. An outside link shows its host after the text and opens through a sheet that shows the full address first; a Nook link opens in Nook. Your own messages stay plain text.
- **Images in replies.** A picture from this Nook (a file or whiteboard you can open) and a small picture embedded in the reply itself (PNG, JPEG, GIF, or WebP, up to 2 MiB) show at once; a picture you cannot open shows a neat "could not be shown". **A picture from another site never loads by itself**: a card shows its description and the site's full address, with **Load image** and **Open link**. **Loading it sends its address (including anything after “?”) to that site**, through Nook, so the site does not see your address; Nook loads only real PNG, JPEG, GIF, or WebP pictures up to 5 MiB from public https addresses, 60 a minute, and never follows a redirect; anything else shows "That image could not be loaded". **Always load images from <site> in this chat** loads that site's pictures in this chat until you reload the page. SVG pictures are never shown. Tap a picture to see it full size; Back closes it. Pictures a tool returns show in **Used N tools** under the call ("Image it returned"); they count toward your storage quota (each picture once, however many chats keep it), and none is kept when your quota is full. The model is only told whether a picture was shown. On a public link, only pictures embedded in the reply show; other pictures stay as a chip.
- **Edit** a message of yours to send a changed version: it becomes a sibling of the original, and a **‹ 2 / 2 ›** switcher on the message moves between versions (nothing is deleted). **Regenerate** on a reply asks again as a sibling, with the same switcher; **Retry** does the same after an error, a stop, or a server restart ("Stopped: server restarted"). **Copy** copies a reply as text. Each reply shows its token count ("1,204 tokens", "est." when the provider reports none).
- **The budget.** Under the composer, "12% of today's tokens" shows how much of your daily token budget is used (it resets at midnight UTC); once it is used up, sending is refused until then, and the whole Nook may have a budget too.
- **⋯** on a chat: **Rename**, **Pin**, **Move to Bin** (30 days in the Bin, under the **Chat** items; a running answer stops). Deleting an agent moves it to the Bin too; its chats stay readable and can continue once it is restored.
- **Errors** are shown under the reply with **Retry**: the provider did not answer or refused the key, the provider stopped answering, today's budget is used up, or no provider is configured.
- **Tools.** An agent with tools may call them while answering: a reply shows **Used N tools**, which opens to one row per call ("Called github/search"), each with the arguments the model wrote, an excerpt of the result (never the whole thing), how long it took, and how it went. A tool that is not read-only **asks first**: a card appears in the chat ("The agent wants to run create_issue on github", with the arguments) with **Deny** and **Allow once**. Nothing runs until you answer, and the answer's time limit does not run down while the card waits; after 15 minutes without an answer the call is marked **Not answered in time**, the model is told you did not answer, and the reply goes on without it. If you press Stop (or the answer runs out of time) while a card waits, the call is marked **Stopped before an answer**. A stopped answer keeps what it wrote and counts the tokens it used toward your daily budget. A reply longer than Nook stores (256 Ki characters) is cut and ends with "[truncated: the reply was longer than allowed]"; it counts the prompt plus the kept text (about one token per four characters, shown as "est."), not the text past the cut. When an answer uses tools, the text of each step before a tool call went back to the model and counts in full; the last step counts only what still fit in the reply. If you lose the right to chat while an answer streams (your role changed, or the agent went to the Bin), it stops within a couple of seconds and says so. Reloading the chat brings the card back, and so does coming back to the chat after leaving it: Back while a card is showing leaves the chat, and the card waits there for you. A tool whose server the admin disabled, removed, or edited (a new URL or credential, say) while the card waited is not run, even if you allow it: the call says the server changed. If your linked key lost a permission the call needs in the meantime, the call says which one (for example, a proposal needs **Inbox write**), and if the key was revoked or expired it says so. Results reach the model marked as untrusted data and cut to a size the admin sets.
- **Nook's own tools** work only through **a Nook key you own**: ⋯ → **Link Nook key** (or the agent editor) lists your live API keys with their grants (never a key that can **Run agents**: an agent's tools must not be able to start other runs, so such a key cannot be linked, and a linked key cannot be given that permission); the agent then reads what that key may read, its reads count against the key, and nothing of your own session is used. By default a change the agent wants to make in your Nook becomes a **proposal in your Inbox** (the card says so; approve it there or reject it), which needs a key with Inbox write and the module's read grant. Whatever the agent reads through the key is sent to the model provider.
  If the linked key is revoked or expires, the agent editor says **Key revoked — link another** (or expired), explains "The linked key was revoked" (or "has expired", "is inactive"), the picker lists none of Nook's tools until you link a live key, and a reply that tries one says the key is no longer active. A note change the agent proposes is saved as a draft for your review; the published note does not change until you approve it.
- An agent that can read your Nook and reach an outside service shows a badge: **This agent can read your data and reach outside services. Content it reads could steer it.** Such an agent asks before every call to an outside tool that is marked open-world, even one the admin lets run on its own.
- **Sharing an agent.** In **Settings → Agents**, an agent's **Share…** opens the Access sheet: only you, people and groups you choose, or everyone signed in (never guests). **Can view** lets them chat with it; they see its name, description, model, and starters, never its prompt or tools. **Manager** also lets them edit and share it (at Can view); only you can move it to the Bin. When a manager changes its prompt, its tools, or direct Nook writes (or the change makes it read your Nook and reach outside services), you get a notice in the bell naming them. A manager does not see the tools you picked from servers they cannot use; the editor counts them ("2 tools from servers you can't use are also picked") and their saves keep them. Prompts are not secret: the model can repeat them. Agents shared with you are listed under **Shared with you**; one you may only chat with opens as a page with its description and **Link Nook key**. Its Nook tools always run through **your own** linked key, never its owner's.
- **Sharing a chat.** ⋯ → **Share…** on one of your chats (members and admins) shares it read-only with people, groups, or everyone signed in. *People you share with see tool calls and results, including anything the agent read from your Nook.* They find it under **Shared with me** in the chat list and follow it live: with the chat open, your new messages and the agent's reply appear as they happen. They see the branch on your screen only, never your other versions of a message, and never the **asks first** cards, which only you answer. To reply, they use **Continue as a copy** (the header) or **Continue from here** (on any message): a new private chat of their own with the conversation up to that point, marked "Copied from <name>'s chat". It runs as them, with their own key and budget, and you never see it. They need the agent shared with them too; if it is no longer shared with them or its owner moved it to the Bin, their copy says the agent is no longer available.
- **Public links** (only when an admin allows them in Settings → AI): ⋯ → **Public link…** makes a snapshot of the chat as it is now, readable at `/share/c/…` by anyone with the link, without signing in. Copy the link when it is created: it is shown once. Tool calls show by name; tick **Include tool results** to show their arguments and results. **Update link** refreshes the snapshot; **New link** replaces the link; **Revoke** turns it off at once. Moving the chat to the Bin hides the link until you restore it; so does your role dropping below member (or your account being blocked), until it is back.
- **The Bin and sharing.** While a shared agent or chat is in the Bin nobody else can open it; restoring it brings its sharing back.
- **Audit log.** Runs of your agents through an API key or MCP (see *Running agents from scripts* under [The REST API](#the-rest-api)) never appear as chats; they are in **Audit log**, linked under the chat list once you have such a key (admins always see it). It lists cards (the agent, the key and how it called, the status, steps, tool calls, tokens, how long it took, and when), newest first, with **Filters** (key, agent, status, dates) in a sheet: every key and agent of yours is offered, even one with no runs yet, and the filters are part of the address (`/chat/audit?key=…&status=failed`), so Back returns to the previous filters and a filtered list can be bookmarked. A card opens the run as a timeline: the input on top, each model call with its text and tokens, each tool call with its server, outcome, and time (open it for the arguments and the result, each kept up to 16 KiB), and the output at the bottom rendered as Markdown. **Export** downloads your runs as JSON: one run from its page, or up to 1,000 matching the filters from the list. Admins see every key's runs as metadata only (agent, key, owner, status, counts, tokens, timings, and tool names), never what was asked or answered. Runs are kept for 30 days unless the admin set another period. On a phone the list and a run are two screens: Back returns to the list, Forward reopens the run, and Back closes the filter sheet first.

| `/chat/new` (optionally `?agent=<agent-id>`) | A new chat, with the agent to pick or preselected |

## Settings

**Settings** is a page of its own at `/settings`. Open it with **Settings** in the account row or the Notes and Files sidebar footer. On a computer a nav on the left lists every section and the section you chose fills the rest of the window; the nav and the section scroll on their own. The header over the section shows your picture, name, team role, and the section's name.

- **Account:** **Security** (password, two-factor, Google sign-in), **Notifications**, **My access** (not for guests), **API keys**, **Agents** and **Knowledge** (not for guests), **AI** (admins), **Modules**, and **About**.
- **Workspace:** **Bin** ([Bin](#bin)), for everyone except guests (a guest can delete nothing, so their Bin is always empty), with its item count. It is hidden while the Bin module is off or for a guest, and `/settings/bin` then opens **Security**.
- **Team:** for everyone but guests, **Members** (admins see the number of blocked accounts beside it); admins also get **Invites**, **Groups**, **Integrations**, **Keys**, **Policies**, **Templates**, **Access activity**, and **Email log**. Members, viewers, and guests see Team only while the Team module is on; admins always keep it here.

Each section has its own URL (`/settings/security`, `/settings/keys`, `/settings/bin`, `/settings/team/groups`, …), so Back and Forward move between the sections you opened and then back to where you opened Settings. Older links still work and are rewritten in place: `/team/…` opens the same Team screen under `/settings/team/…`, `/bin` opens `/settings/bin`, and `/settings/mcp` opens `/settings/keys`, whose tabs are `/settings/keys/general`, `/settings/keys/vault`, and `/settings/keys/agents` (see [API keys](#api-keys)).

**On a phone** Settings opens on the section list, with your name and role at the top. Tapping a section opens it as a screen of its own, with a back arrow in its header. The arrow and browser Back return to the list, a second Back returns to where you opened Settings, and Forward opens them again. A section opened from elsewhere (**Open Bin**, **Leaving the Bin soon** on Today, **Turn on in Settings**, a notification, or a link) opens with the list under it, so it goes back the same way. Inside Team, a person, a group, or an integration is one more screen with its own back link.

Opening a Settings link directly (from an email or a bookmark) puts Home under it: Back from Settings goes to Home rather than off Nook. A guest who opens **My access** by its address sees **Security**; someone who is not an admin and opens an admin-only Team address sees **Members**, with a note saying that section is for admins.

While a new API key is on screen (it is shown only once, in **API keys** or on an integration's page), leaving it by another section (the Bin included), the back arrow, Home, Inbox, the bell, **Sign out**, or browser Back or Forward asks first. Unsaved changes in **Team → Policies** ask the same way (Discard or Keep editing).

### Settings → Agents

**Agents** lists your agents and opens an editor for each (`/settings/agents/<agent-id>`; on a phone a screen of its own below the list, with its own back link): **Basics** (name, description, an emoji), **Instructions** (the system prompt, with its character count; a fixed preamble goes before it that marks tool results and documents as untrusted and forbids revealing secrets, so put no secrets in a prompt, and the prompt is not secret from people you later share the agent with), **Model** (**Provider**: **Default (<name>)** follows whichever provider an admin makes the default, now and later, or pick one of the admin's providers by name; anyone who may create agents sees their names and default models, never their addresses or keys. **Model**: empty uses the provider's default model, which the placeholder names; the list suggests the models the admin's last **Test** of that provider found, or just its default model, and any typed id works with **Use “…”**. When a provider is deleted, its agents go back to the default. Managers of a shared agent may change both; people who can only chat with it see the provider's name. The agents list shows the provider's name when an agent has its own. **Max steps**, the model calls per answer, 8 by default, which matters once tools arrive; temperature), and **Starters** (up to four prompts offered on an empty chat). **Tools** lists every tool server you may use (expanded to its tools, each with its badges: read-only or not, open world, and the admin's policy; tick what the agent may call, and make a tool stricter than the admin's policy with **Ask first** or **Off**, never looser) and **Nook**: once you **Link Nook key** (one of your own live API keys with the MCP surface; the sheet shows each key's grants), Nook's tools the key reaches appear by module, read tools marked read-only and writes marked **Proposal · asks first**. **Allow direct Nook writes** lets writes happen directly instead of as Inbox proposals, only with a key that holds the write grant, and they still ask first. An agent that mixes Nook's tools with an open-world remote tool shows the trifecta warning. Save keeps the version you edited: if someone changed the agent meanwhile, "Changed elsewhere · Reload". **Chat with it** opens a new chat; **Move to Bin** keeps it 30 days. Below the form, **API and MCP runs** counts the agent's runs through keys over the last 30 days (runs, failures, and tokens per day; never their content, which is in the key owner's Audit log). Sharing and knowledge bases come in later releases.

### Settings → Knowledge

A **knowledge base** is a set of texts your agents can search: published notes, text, Markdown, or CSV files from Files (1 MiB at most each), and pasted text (256 KiB at most), up to 500 sources. **Knowledge** (`/settings/knowledge`, not for guests) lists yours and those shared with you; **New knowledge base** asks for a name and a description (agents see the description). Each base has a page of its own (`/settings/knowledge/<id>`; on a phone a screen below the list with its own back link):

- **Anyone who can use an agent with this knowledge base can read its text.** The page, Add source, and the share sheet say so. Its whole text is also sent to the model provider when it is indexed, and the passages an agent finds go to the provider with the agent's answer.
- **Add source** (owners and managers) offers **Note** (published notes), **File** (files named `.txt`, `.md`, or `.csv`; other files, such as `.json`, are refused), or **Paste text**. Only notes and files that **both you and the base's owner can read** are listed: the base reads them as its owner, and a manager can never add one of the owner's private notes, or one of their own that the owner could not read.
- **Sources** show their state: **Waiting**, **Paused** (the owner's or the instance's daily token budget is used up: every waiting source says so, and indexing resumes after midnight UTC, or as soon as an admin raises the budget; the page then checks only once a minute), **Indexing**, **Ready** (with the number of passages), **Error** (with the reason, such as the provider refusing), or **Unavailable** (the owner can no longer read that note or file; its passages were removed, and it comes back if they can read it again). The status line names errors ("1 source has an error") rather than saying Ready. The page refreshes while anything is indexing. Publishing a note that is a source re-indexes it about a minute later. A note or file that is unshared from the base's owner, moved to the Bin, or deleted forever leaves the base **at once** (a note or file deleted forever also loses its title there: it shows as "Deleted note" or "Deleted file"); a restore brings it back. Notes and files are also checked every hour, and a search never returns a passage whose note or file the owner can no longer read. Removing a source removes its passages at once; the note or file itself is not changed.
- **Re-index all** embeds every source again (after a provider or model change upstream, for example), at most once an hour per base, for its owner too (a restart of the server does not reset that hour); sooner, it says how many minutes to wait. Indexing costs tokens from the owner's daily budget.
- **The provider stays until the owner changes it.** A base keeps the model provider, embedding model, and size it was made with. If an admin points that provider at another address, every source is embedded again. If the provider is removed, the page says so, every source shows "The embedding provider was removed", nothing new is indexed, and search (Try it and agents) works by keywords only, until the owner picks another provider with **Change embedding model**. A base is never moved to another provider on its own.
- **Change embedding model** (the owner only) picks a provider (by name), a model (the provider's known embedding models are offered; any model id works), and, for `text-embedding-3` models, the size (64 to 3,072 dimensions). Since 2026-10-08 an admin can limit this per provider (Settings → AI → Model providers → Knowledge bases): only the providers they allow are offered; when they listed models you pick one of those (no other model id); and the size field stops at their limit, which it states. A model that answers in its own size larger than the limit stops at its first answer: every waiting source shows the error, and you choose another model. Before anything changes, Nook asks you to confirm what it costs: **every source is embedded again at your token cost, search uses keywords only until that finishes, and the old vectors are deleted at once.** While it runs the page says the base is moving to another model, Try it and agents match by keywords only, and Waiting sources show progress as usual (over your daily budget they wait, Paused, as any indexing does). It counts as the base's Re-index for the hour, except when its provider was removed: then you can change it at once.
- **Passages of a source.** The owner, and managers who can open the note or file themselves (pasted text: every manager), can expand a source with the arrow beside it to see its passages: each one's heading path and its first 300 characters, with the number of passages, 20 at a time with **Show more**. People who can only search the base (Can view) never see this list; they see passages only as Try it and agents return them. A base is never moved to another provider on its own.
- **A blocked owner.** While a base's owner is blocked, the base is paused: nothing is indexed and it answers no searches (Try it, agents, or keys), as the owner's agents stop. It resumes when they are unblocked.
- **How text is split.** Markdown headings become each passage's **heading path** ("Billing › Refunds"); a heading that asks a question, or a `Q:` / `A:` pair, stays one passage with its whole answer; long sections are cut at about 3,200 characters with a little overlap; a CSV file goes in 20-row passages that each repeat the header row.
- **Try it** searches the base the way an agent would and shows the top passages with their heading paths, scores, and where each ranked by meaning and by keywords. A search costs a few tokens; if the model cannot be reached it says it matched by keywords only.
- **Share…** opens the Access sheet: **Can view** lets people search it (Try it); **Manager** also lets them add and remove sources, rename, re-index, **attach it to agents**, and share it at Can view; only the owner moves it to the Bin. **What managers see:** the title of every source, including notes and files they cannot open themselves. Viewers do not see the title of a source note or file they cannot open, and the heading paths they see leave out that note's own title (its first heading); the headings inside the note still show.
- **Move to Bin** (the owner): agents that use it stop finding it at once; it stays in the Bin under **Knowledge** for 30 days, and restoring it brings back its sharing and its agents' use of it.

**Using a base in an agent.** In the agent editor's **Tools**, the **Knowledge** group lists the bases you own or manage; tick the ones the agent may search (the agent's owner must own or manage them too). A base shared with you at **Can view** can be searched in Settings → Knowledge but not attached. A base stays in use only while the agent's owner owns or manages it: if they are moved down to Can view, it stops answering at the agent's next step, like a base in the Bin, and its tick reads "You no longer manage this knowledge base" until it is cleared. They become one read-only tool, `search_knowledge`, that runs on its own (it never asks first) in chats, over the API, and over MCP. A reply that used it shows **Searched knowledge** under **Used N tools**, with the passages it found and their heading paths. **What the agent sees is deliberate:** the passage text always, but the name and link of the source note or file only when the person chatting can open it themselves; someone you share the agent with gets the answer, never the title of your private note it came from. An agent with a knowledge base and an open-world tool shows the badge about reading your data and reaching outside services.

### Settings → AI (admins)

**AI** holds the **model providers** and the **chat policy**. A provider is a name, an OpenAI-compatible base URL (`https://api.openai.com/v1` by default; a private-network host such as an Ollama or LiteLLM container must be listed in `AGENT_ALLOWED_PRIVATE_HOSTS` on the server), an API key (**encrypted at rest; anyone with the server and its key can read these secrets**; after saving, only `sk-…a1B2` is shown, and leaving the field empty on an edit keeps the saved key), a default chat model (`gpt-6-luna` to start), and compatibility options (the output-token parameter, whether the server reports usage while streaming, the context window). Under **Knowledge bases** (2026-10-08) you choose whether knowledge bases may use the provider at all, which **embedding models** they may use (**Any model**, or **Only these**: a list of up to 20 model ids, picked from the provider's model list, embedding models first, or typed), and the **largest size** in dimensions (64 to 3,072; empty means no limit). A 3,072-dimension base takes six times the storage and memory of the 512 default. A new knowledge base takes the default provider's embedding model and size, moved inside its limits (the first allowed model, at most the largest size); if the default provider is not allowed for knowledge bases, new ones cannot be made. Bases made before a limit keep working as they are and are never embedded again on their own; their page says the admin's limit is lower, and **Change embedding model** offers only allowed choices. **Test** lists the provider's models and runs a one-token completion, reporting counts and latency. One provider is the **default**; at most five. **Tool servers** are MCP servers (Streamable HTTP) agents may call: a name, a URL (a private host must be listed in `AGENT_ALLOWED_PRIVATE_HOSTS`), authentication (none, a bearer token, or a custom header; the credential is encrypted at rest and shown only as `abc…wxyz`), a per-call timeout, a result cap on what the model sees, and who may attach its tools (admins only, or everyone who can chat). **Sync tools** lists the server's tools with badges (read-only or not, open world, destructive) and a **policy** each: **Auto** only for tools the server marks read-only, **Asks first** for the rest, **Off** to hide one; a later sync never loosens what you set. **Disable** keeps a server but drops its tools from every agent at the next step; **Remove** deletes it and its credential. With `AGENT_MCP_STDIO=on`, the servers the host declared appear read-only below ("Declared by the host · runs as Nook's user") with **Adopt**. The **policy** sets who creates agents, who chats (someone whose role cannot chat has no Chat tile, and a Chat link shows "Chat is off for your role"), tokens per person per day, tokens for the whole Nook per day, and agents per person. **Usage** (`/api/agents/admin/usage`) is counts per day per person or agent; admins never read chats. When the server has no `AGENT_SECRETS_KEY`, the page says what to set.

## Settings → Modules

Open **Settings → Modules** to choose which parts of Nook you see. Each module has a switch, and every module is on until you turn it off. A change applies at once and is saved to your account, so it follows you to every device you sign in to (another open tab picks it up when you return to it). Home and Settings are always on.

| --- | --- |
| Notes, Files, Tasks, Collections, Calendar | Its tile on Home and its Today sections (for Files, also Storage). Opening one of its URLs, from a bookmark, a link, Back, or a notification, goes to Home with a one-line hint and a **Turn on in Settings** button. |
| Search | The search box in Notes and <kbd>Ctrl</kbd>+<kbd>K</kbd> / <kbd>/</kbd>, and the **Filter cards** text box on Tasks boards (a text filter from a link still applies and shows as a chip you can remove). The note list and the other board filters stay. Pickers inside other apps keep working. |
| Bin | **Settings → Bin** (`/settings/bin` opens Security) and **Leaving the Bin soon**. Deleting still moves items to the Bin, and they are still deleted forever after 30 days; turn the Bin back on to restore something. |
| Notifications | The bell and `/notifications`. Reminders are still created, and push notifications still arrive on devices where you turned them on. |
| Inbox | The **Inbox** button, `/inbox`, and **Proposals awaiting you**. Agents can still suggest changes while it is off; nothing is applied until you approve it. Guests do not see this row. |
| Vault | Its tile on Home and `/vault`. Hidden for guests, and for everyone but admins while the server has no vault key (then there is no switch either). |
| Chat | Its tile on Home and `/chat`. Hidden for guests, and for everyone but admins while the server has no agent key (then there is no switch either). Agents, chats, and the Bin's Chat items stay as they are. |

**Back and Forward past a module that is off.** Back steps over an entry of a module that is off to the page before it. Forward cannot pass beyond such an entry: it stays where you are and shows the hint. For example, after Home, then Team, then Calendar, with Team turned off and Back to Home, Forward stops at Home, and Calendar is not reachable with Forward. Turning the module back on restores it: Forward then goes to Team and on to Calendar again.

**A hidden module is not a security boundary.** Turning a module off only hides it in this app for you. Nothing is deleted, sharing is unchanged, people you share with still see what you share, MCP keys keep every permission they were given, and calendar feed links keep working. To stop an MCP client or a feed, revoke its key or link instead.

## Email

When your admin has set up email (OPERATIONS → Email), Nook can email you about things that involve you. Open **Settings → Notifications** and scroll to **Email**; the direct link is `/settings/notifications`. Settings has a URL for each section (`/settings/security`, `/settings/keys`, …; see [Settings](#settings)).

- **Verify your address first.** An account made with an invite sent to your address is already verified. Otherwise Nook emails you a verification link when you sign up; open it (it works once, for 24 hours) or press **Send verification email**. Until you verify, Nook sends you only security emails.
- **What Nook emails.** *Assigned to you* (someone else adds you to a card), *Comments on your cards* (cards you created or are assigned to), *Shared with you* (a note, folder, file, board, calendar, collection, or task view shared with you by name; sharing with everyone sends nothing), and *Proposals awaiting you* (your MCP keys suggested changes: only the key's name and how many, never the agent's text). Each has its own switch, and **Email notifications** turns them all off at once. Nothing you do yourself emails you.
- **Grouped, not noisy.** Emails of one kind wait up to 10 minutes and arrive together ("Priya assigned you 3 cards on Launch"); proposals wait up to an hour and come at most every 3 hours. If you lose access to an item before the email goes out, it is left out.
- **Security emails are always on**: a new MCP key on your account, your team role changing, two-factor turned on or off, new recovery codes or a recovery code used, your password being changed or reset, a sign-in from a device or browser your account has not used before (see [Recognised devices](#recognised-devices)), and your account being blocked, unblocked, or signed out everywhere. If one of these was not you, act on it straight away.
- **New sign-in.** When someone signs in to your account (with a password, with Google, or by finishing two-factor) from a browser that is not on your [Recognised devices](#recognised-devices) list, Nook emails you the time (in your time zone), the browser and system (for example "Firefox on Linux"), and how it signed in, with **Review security settings** and "Wasn't you? Change your password and sign out other devices". It never shows an IP address. Several such sign-ins within 10 minutes arrive as one email. It goes only to a verified address, and not for the sign-in that creates your account. The same line appears under the bell ("New sign-in from Firefox on Linux"), even when email is off.
- **Welcome.** A minute after you first sign in to a new account (by registering or accepting an invite), Nook sends one welcome email with links to Today, your notification settings, and the documentation. It goes once, and only to a verified address: if you verify later (within 7 days), it comes then. Accounts from before this feature never get it.
- **Quiet hours** hold activity emails until they end, in the time zone shown under them (**Use this device's time zone** changes it). Security emails are never held.
- **Send me a test email** checks that mail reaches you (3 an hour).
- **Unsubscribe.** Every activity, reminder, and digest email has a link at the bottom that turns off that one kind of email (or the digest); the page asks before it changes anything. Mail apps that offer an "Unsubscribe" button use the same switch. Security emails cannot be turned off.
- **Digest.** Under **Summary**, choose **Daily** or **Weekly (Mondays)** and a time. It arrives at that time in your time zone (also across daylight-saving changes) and lists your own cards that are overdue or due soon (today and tomorrow for daily, the week for weekly), your events in the next 7 days, proposals awaiting you (key names and counts), and what was shared with you by name since the last digest. Each line links to its card, event, Inbox, or item; **Open Today** opens Today. Empty sections are left out, and a digest with nothing in it is not sent. It is off until you turn it on, and it is never scheduled inside quiet hours: a time inside them moves to when they end. The line under it says when the next one goes. Once your address is verified and your account is a week old, Today asks once, **Get a morning summary by email?**, with **Every morning**, **Mondays only**, and **No thanks**; any answer (or choosing a cadence here first) puts the question away for good.
- **Reminders by email.** In Calendar, **Add reminder** has **Remind me by**: *Notification* (the bell and push, as before), *Email*, or *Notification and email*. Email needs a verified address that has not bounced, with **Email notifications** and **Reminders by email** on; otherwise the email choices are greyed out and the sheet says why. An email-only reminder still appears under the bell but sends no push. Reminder emails arrive at the reminder's time **even during quiet hours** (you set that time on purpose), and say "(late)" when Nook could not send them within 15 minutes. **Reminders by email** also covers *event changed* and *event cancelled* emails: when someone else moves an event you set a reminder on to a new time or place, or moves it to the Bin, within the next 7 days, you get one email (changes within 10 minutes are grouped, and a change that is undone sends nothing).
- **Sprints** (off by default): an email when a sprint with cards assigned to you starts or is completed, with your own cards' counts. **Bin clean-up** (off by default): at most once a week, a list of items in your Bin that will be deleted for good within 3 days.
- **Mute a board or calendar.** In a board's **Board settings → Email**, tick **Mute emails from this board**; in Calendar's **Calendars** sheet, use the mail button on a shared calendar; its line then reads **Muted**. Nook then sends no activity email about it (assignments, comments, sprints, event changes); your own reminders, the digest, and security email still come. **Settings → Notifications → Email → Muted** lists everything you muted, each with **Unmute**.
- **Bounced email.** If mail to your address bounces or is reported as spam, Nook stops emailing it (security emails still go) and Settings shows a red notice. A run of temporary bounces pauses email for 3 days and then resumes by itself. **Try again** turns email back on straight away (once a day).

Emails link straight to the card, note, board, Inbox, or Settings section they are about, on this Nook's address. Nook never asks for your password by email, and its emails contain no images, trackers, or remote content.

Admins see what Nook emailed in **Team → Email log** (`/settings/team/email`): which kind of email, to whom, when, and whether it was sent, held, skipped (and why), or failed, with a **Retry** for failed ones. A **Bounced**, **Spam report**, or **Soft bounces** tag next to a name means Nook is holding back all but security email to that person's address. It never shows addresses, subjects, or content.

## Password

**Change it** in **Settings → Security → Password** (`/settings/security`): press **Change password**, enter your current password, the new one twice (at least 12 characters), and, if you use two-factor authentication, a code from your app or a recovery code. Every other device signed in to your account is signed out; the one you are using stays signed in. Nook emails you that the password changed. This works whether or not email is set up. Your API keys keep working, so review them under **Settings → API keys** if you changed the password because something looked wrong.

**Two-factor recovery codes.** When you turn on two-factor authentication in **Settings → Security**, Nook shows your recovery codes in their own window with **Copy all** and **Download**; Nook stays on Settings until you press **I saved them**. Each code signs you in once if you lose your authenticator app.

**Forgot it?** On the sign-in page press **Forgot password?** (`/forgot-password`), enter your address, and press **Send reset link**. The page always answers "If that address has a verified account, we sent a link": it never says whether an account exists. The email arrives only when the account's address is verified and the account is not blocked. Its link works once, for 30 minutes, and a newer link replaces an older one. Open it, choose a new password, and, if the account uses two-factor authentication, enter a code from your app or a recovery code (a mailbox alone cannot take over the account). Resetting signs you out on **every** device, including this one, and does not sign you in: sign in with the new password. Nook emails you that the password was reset, with a link to review your API keys, which keep working.

When email is off on your Nook, the forgot page says so and sends nothing: ask an admin. Admins cannot send a reset email for someone else.

### Recognised devices

**Settings → Security → Recognised devices** (`/settings/security`) lists the browsers that signed in to your account, most recent first, with when each was first and last seen; the one you are using says **This device**. Nook recognises a browser by a random cookie it sets when you sign in. It keeps only a fingerprint of that cookie and the browser and system names ("Safari on iOS"), never the full browser string or your IP address, and at most the 20 most recent devices.

- A sign-in from a browser not on the list sends you a **New sign-in** email and a bell notice. A new browser, a private window, or cleared cookies all count as new, so if it was you, ignore it.
- **Forget** removes one device from the list, and **Forget all** removes every one. Forgetting signs nothing out; the next sign-in from that browser is new again. To sign other devices out, change your password.
- Both ask first in Nook's own dialog; Back (or Escape) closes it without changing anything.
- An admin blocking your account, or resetting it for Google sign-in, clears the list.

## Team

Changing a role, blocking, unblocking, or signing someone out everywhere asks you to confirm in a dialog; there is no password re-check for signed-in admins.

**Team** lives in [Settings](#settings): **Settings → Team → Members** lists everyone with an account on this Nook and their **team role**. Open it from the Settings nav (**Settings → Team → Members**; the top bar has no Team button since Wave 38), or at `/settings/team/members` (the old `/team` still works). Each person has their own page at `/settings/team/members/<id>`, next to the list on a computer.

- **Roles.** An **Admin** can do everything a member can, and manages the team. A **Member** creates, edits, and shares notes, files, tasks, collections, and events, as before. The first account created on a new Nook is the admin; when an existing Nook upgrades, the oldest account becomes the admin and everyone else a member (the operator can change it, see [OPERATIONS.md](OPERATIONS.md#team-admins-and-blocking)). A **Viewer** reads everything shared with them or with everyone, but creates, edits, shares, and uploads nothing. A **Guest** reads only what is shared with them by name: items shared with "Everyone here" are not shown to guests. New accounts are guests unless the operator chose otherwise (`SIGNUP_ROLE`). The team role is separate from the levels you give when you share (Can view, Can edit, Manager): it caps them, so a viewer or guest only ever reads, even where others can edit.
- **Viewers and guests.** Each app shows a **View only · Team role: Viewer** (or Guest) banner and hides the create, edit, share, upload, and delete controls, also on items the person created before their role changed (those stay theirs and stay shared). They can still read, download, search, use Today, run task filters (guests: only "Assigned to me"), set their own reminders on events they can read, manage their notifications, push devices, two-factor, and Modules, and sign out. Viewers can save, rename, duplicate, and delete private task views (**New view**, **Save as view**) but cannot share them; guests save no views and see only views shared with them by name. They cannot restore or empty the Bin (items leave after 30 days) or create calendar subscribe links. In Settings → API keys a viewer can create keys with read permissions only, and a guest cannot create keys. Guests have no Team in Settings. When you share with people, the list marks recipients who will only read with **Guest** or **Viewer**.
- **What you see.** Everyone sees names, team roles, and whether an account is blocked. Admins also see each account's email, when it was last seen, whether two-factor is on, how many API keys it has, how much storage it uses, and its activity. Admins never see anyone's private notes, files, or other content.
- **Search and filter.** Search by name (admins also by email) and filter with the chips: All, Admins, Members, Blocked, and Viewers or Guests once someone has those roles. Accounts created in the last 7 days carry a **New** tag for admins.
- **Changing a role** (admins). Pick the role on the person's page and confirm. Making someone an admin, or removing admin, asks for your password (and a fresh six-digit or recovery code when two-factor is on). Nook always keeps at least one admin: the last one cannot be demoted or blocked. If someone else changed the role meanwhile, Nook shows the current role instead of overwriting it. A change applies on the person's next click.
- **Blocking** (admins). **Block** signs the person out on every device at once and stops them from signing in; you can add a reason that only admins see. Their MCP keys and calendar links pause, and their content stays where it is, still shared as before. Blocking an admin asks for your password. A blocked person who signs in with the right password is told the account is blocked. **Unblock** lets them sign in again with their existing password and two-factor code; they need to turn push notifications on again on each device.
- **Sign out everywhere** (admins) ends every session of that account without blocking it.
- **Activity** (admins) lists the latest role changes, blocks, unblocks, and sign-outs for the person, who made them, and when, including changes made from the host command line.
- **Access** (admins, `/settings/team/members/<id>/access`) shows everything the person can open that others own, and through what, with reductions only: remove or lower a direct share, take them out of a group, revoke an API key, **Revoke** one calendar feed link, **Pause** one routine, or **Reset access** (all of it at once). A feed's calendar is named only when you can open it yourself; a routine shows its name, schedule, and key, never its instructions. Only the person can resume a routine you paused. Each action asks first in a dialog (Back cancels), is recorded in **Team → Access activity**, and the person sees it in their bell. The person sees the same lists in **Settings → My access**, where they can revoke their own feed links (viewers too) and pause or resume their routines (members and admins).
- **Google sign-in** (admins, when Google sign-in is on). The person's page says whether they sign in with Google, which Google accounts can link their address (a Google Workspace account of the address's domain, or the Gmail account itself), and the last Google sign-in that could not link, with the time and why. **Allow Google sign-in…** lets their next Google sign-in link the account, once, within 24 hours. **Reset account for Google sign-in…** is for an account nobody knows the owner of: it signs it out, removes its password, two-factor, keys, feed links, and sharing, and keeps its content. It is not the same as **Reset access** under **Access**, which removes what others share with the person. For a linked account, **Allow re-linking…** is for someone who recreated their Google account: whoever next signs in with Google as that address gets the account and everything in it, so their old sessions, keys, and feed links end then, and by default the password and two-factor go too (you can keep them when you are sure the same person re-links). Each of these asks for your password (or a Google confirmation) and your two-factor code, and the person sees it in their bell.

On a phone, the list and a person's page are separate screens: Back closes an open picker or confirmation first, then returns from the page to the list (the page's **‹ Members** link does the same), then to the Settings section list, then to where you opened Settings. The **Team** button opens Members with the section list under it, so Back and the back arrow both return to the list.

### Groups (admins)

**Team → Groups** (`/settings/team/groups`) lists the groups on this Nook with their size. **New group** asks for a name and an optional description; a group's page (`/settings/team/groups/<id>`) adds people with the type-to-search field, removes them, renames or deletes the group, lists what owners shared with it (with the title hidden when you cannot open the item yourself), including agents, chats, and knowledge bases shared with the group, and shows its history. The "Shared N items" count counts those too. Adding someone to a group, removing them, or deleting the group takes effect on their knowledge bases at once: a note they could read only through the group leaves their bases' passages (Unavailable), and comes back when they rejoin.

- A group never opens anything by itself: owners choose to share an item with it at a level, and you decide who is in it. Everyone in the group then reaches what was shared with it, from their next click; someone you remove loses it at once.
- You can add yourself; the group page, its history, and the owners' Access sheets say that an admin added themselves.
- Guests in a group only ever read. **Delete group** says how many items were shared with it; those shares end, and everyone's own and direct shares stay.

On a phone, Back returns from a group to Groups, then to Team.

### Keys and policies (admins)

- **Team → Keys** (`/settings/team/keys`) lists every live API key on this Nook: its name, owner, permissions, surfaces, expiry, last use, and 14-day use, filtered by owner, module, state (expiring within 14 days, no expiry, blocked by policy, in rotation grace, expired, unused for 90 days), surface (MCP or REST), and whether a key is limited to addresses. You never see a key's secret or the names of the items a key is limited to. **Revoke** asks for a reason, stops the key at once, and shows the owner that an admin revoked it and why.
- **Team → Policies** (`/settings/team/policies`) sets the rules every key follows, checked on every call: the longest lifetime and the default for new keys, whether every key must have an expiry (keys made before this release have none), how many live keys each person may hold, which team roles may use keys over MCP and over REST, which modules each role's keys may use, and whether anyone may share with guests (off: nobody can share with a guest, directly or through a group, until it is turned back on; existing shares with guests stay until they are removed, see [Guests](#sharing-and-access)). The line above **Save policies** says how many keys a change would block. A key that breaks a rule is **blocked, not revoked**: it stops working and shows **Blocked by team policy** until it complies or the rule is loosened. Two admins editing at once cannot overwrite each other: the second save is refused and reloads.

### Integrations (admins)

**Team → Integrations** (`/settings/team/integrations`) is for AI clients and scripts that should act as themselves rather than as a person: a CI job that posts results, a bot that files cards, an agent that reads a shared folder. Each one is an account that **never signs in**; it acts only through the API keys you create for it, and its keys keep working when the person who set it up leaves.

- **New integration** asks for a name, a role (**Member** or **Viewer**; never Admin), and an optional description. Its page (`/settings/team/integrations/<id>`) changes the role, renames it, blocks or unblocks it, and deletes it; every change asks first and is recorded in Access activity.
- **Keys.** The same list and dialogs as Settings → API keys, for the integration: **New key** asks for *your* password (and code) to create or rotate; Edit narrows without it; the new key is shown once, so copy it into the client that uses it. While it is on screen, leaving the page (← Integrations, another Settings section, Home, or browser Back or Forward) asks first, as in Settings → API keys. Keys cannot hold Inbox or Team permissions. The key's items are chosen only from what owners have shared with the integration. Team → Keys lists them with the integration as owner.
- **What it can reach.** Only what owners share with it by name in their Access sheet. Never what is open to everyone signed in, never a group's items (integrations cannot join groups), and never your own items. Admins hold its keys, so admins can read what owners share with it (owners are told so when they share), and nothing else of theirs.
- **Block** pauses its keys at once; **Unblock** resumes its live keys. **Delete** revokes its keys, then removes it only when it never had a key and never created anything. Otherwise (it had a key, even one that only read, or it created a card, a comment, a note version) it is kept as **Deleted (kept for attribution)**, so its name stays on that content and on its keys' history in Access activity. A deleted integration is final: it cannot be unblocked, renamed, given another role, or given a key; it is not offered in any picker; and it does not count toward the limit of 100 integrations. Deleting it again changes nothing.
- It never receives email or notifications, does not count toward `ALLOWED_EMAILS`, and cannot be invited. It can be assigned a card on a board shared with it (nobody is emailed or notified).

On a phone, Back closes a sheet or confirm first, then returns from an integration to Integrations, then to the Settings section list, then to where you opened Settings. After confirming with Google from an integration's keys, the result shows on that integration's page.

### Inviting people

Admins add people with a single-use **invite link**, even while registration is closed. Open **Settings → Team → Invites** (`/settings/team/invites`).

- **Create.** Choose **New invite**, pick the **Team role** (Member, Viewer, or Guest; Guest is the default; admins are promoted after sign-up) and when it **Expires** (1, 3, or 7 days). Optionally bind it to an **Email** (only that address can use the link) and add a **Label** that only admins see. Nook allows 20 live invites at once and 10 new ones an hour per admin.
- **Copy once.** The full link is shown once, right after you create it: **Copy link**, then send it any way you like. Closing the dialog forgets it; Nook keeps only a fingerprint of the link, so it cannot show it again. Create a new invite if you lose it.
- **Send by email.** When the invite is bound to an email and the operator has set up email, tick **Send by email to <address>** in the dialog, or use **Resend email** on a live invite later. Resending mails a fresh link and the earlier link stops working. Without email set up, Nook says **Email is not configured** and the invite still works by copying the link.
- **Revoke.** A live invite can be revoked; the link stops working at once. Each card shows the role, whether the invite is Live, Used, Expired, or Revoked, when it expires, and who created or used it. A used invite links to the new person's page, whose Activity says "Joined with an invite from <admin>, as <role>".
- **What the invitee sees.** The link opens a **Join Nook** page: "<admin> invited you to Nook as a Viewer", the expiry, and a hint of the bound address. The link leaves the address bar as soon as the page opens. They choose a name, email, and password and land on Today with the invite's role. An expired or already-used link says so and asks them to get a new one from you. Someone already signed in is asked to sign out first.
- **The allowlist still applies.** An invite only opens registration; when the operator sets `ALLOWED_EMAILS`, the invitee's address must be on it.
- **Links die with your admin role.** If you stop being an admin (demoted or blocked), your outstanding links stop working.

## Inbox

The **Inbox** collects changes your MCP keys **suggest** instead of making. Open it with the **Inbox** button next to the bell (its badge counts what is waiting, up to 99+) or at `/inbox`. Nothing an agent suggests changes anything until you approve it, and only you see the suggestions your own keys make.

- **What an agent can suggest:** a new card, a change to a card's fields, a comment on a card, a new or changed event, a new or changed row, or a note draft. Each suggestion is a **proposal**, grouped under the key that sent it, in the order it was sent.
- **Reviewing.** Each proposal shows its kind, the agent's title, the agent's reason under **Written by the agent** (shown as plain text: treat it as the agent's claim, not Nook's), what it changes (for example **Home › To do**), and the changes themselves: a **Before / After** table for fields, or the line diff for a note draft (**Changes** or **Full draft**). On desktop the list and the open proposal sit side by side; on a phone a proposal is its own screen.
- **Approve** applies the change as you, with your access: exactly as if you had made it yourself, and the audit log records that you approved the key's proposal. For a note draft, **Approve and publish** publishes that exact draft as a new version. If the card, event, row, or draft changed after the agent read it, or you can no longer edit it, the proposal is marked **Failed** with the reason and nothing is applied.
- **Reject** takes an optional reason, which the agent can read to learn what not to suggest again. Rejecting a note draft discards it only if it is still the agent's version.
- **Approve all** and **Reject all** act on every waiting proposal of one key, one at a time; the result says how many applied and why any failed. More than ten asks you to confirm first.
- **History** lists approved, rejected, failed, expired, and withdrawn proposals for 90 days.
- **Keyboard** (desktop): <kbd>J</kbd>/<kbd>K</kbd> move between proposals, <kbd>A</kbd> approves, <kbd>R</kbd> rejects.

Proposals expire after **14 days** without a decision (an expired note draft stays in the note). The bell tells you when a key suggests changes ("Key “laptop” suggested 3 changes"); turn on **Settings → Notifications → Push new proposals** to get a push too. The notification and the push name only the key and a count, never the agent's text. **Proposals awaiting you** on Today lists the newest ones.

Viewers can reject proposals that were waiting when their role changed, but not approve them; guests have no Inbox.

## Routines

A **routine** is a prompt you keep in Nook for an agent to run on a schedule: "every weekday at 08:00, look at my boards and suggest cards for anything I forgot". Nook never runs anything itself. Your MCP client (a cron script, Claude Desktop, n8n) asks Nook what is due, runs it, and files what it suggests into the Inbox, where you approve or reject each one as usual.

Open **Inbox → Routines** (`/inbox/routines`) and press **New routine**:

- **Name** and **Instructions**: the prompt the agent runs (up to 16 KiB of Markdown).
- **Can suggest**: the kinds of change it may propose (create cards, update rows, note drafts, …). Nook refuses anything else from the run.
- **Only in** (optional): pin it to boards, calendars, collections, or folders. When you pin a module, Nook refuses that module's suggestions anywhere else; modules you do not pin stay open.
- **Hints for the agent** (optional): guidance such as "only cards tagged #ops". Not enforced.
- **Runs**: Daily, Weekdays (Mon–Fri), Weekly (pick the day), Hourly (pick the minute), or Manual only, at a time in the routine's time zone (your browser's when you create it; **Use <zone>** switches it). A **Schedule note** ("after the Monday stand-up") is shown to the agent.
- **Key**: bind the routine to one key (recommended: only that key sees it), or let any of your keys with **Suggest changes** run it.
- **Max proposals per run** (25 by default, at most 100) and **Expire after** (days its proposals wait, 14 by default).
- **Enabled**: a paused routine is never due. **Pause** and **Resume** are also on each row.

A new routine is due straight away for its current slot (a daily 08:00 routine created at 10:00 can run now); after a run it is next due at the following slot. A missed slot stays due until a run finishes, and several missed slots count once. A run holds a **two-hour lease**; a run that is never finished is marked **Abandoned** by the hourly sweep, its proposals stay in the Inbox, and the routine stays due.

Each row shows when the routine is next due and how its last run went. Open a routine to edit it and to see its **Last runs**: status, when, how many proposals and tool calls (Nook counts these itself), how long it took, whether it hit its limit, and the agent's summary under **Written by the agent**. In the Inbox, a run's proposals are grouped under the routine with the run's time, status, and summary, and **Approve all** works per run. The bell says "Weekly review suggested 4 changes" once per run. Deleting a routine removes its run history; its proposals stay in the Inbox under their key.

Members and admins can have up to 50 routines. If your role becomes Viewer or Guest, your routines are paused.

### Recipe: run a routine from Claude Desktop or a cron script

1. In **Settings → API keys**, create a key with **Suggest changes** plus the read permission for what the routine looks at (for example **Read tasks**), and bind the routine to it.
2. Point the client at `<your origin>/mcp` with the header `Authorization: Bearer <your key>`.
3. The client runs four calls:

   | Step | Tool | What it does |
   | --- | --- | --- |
   | 1 | `list_due_routines` | Lists the routines due now that this key may run. |
   | 2 | `start_run` `{ routineId }` | Returns the instructions, allowed kinds, pins, limit, and the last run's summary and your recent reject reasons, and opens a two-hour lease (`runId`). |
   | 3 | `submit_proposals` `{ runId, proposals: [...] }` | Files suggestions into the run (repeat as needed, up to the limit). |
   | 4 | `finish_run` `{ runId, status: "succeeded", summary }` | Closes the run and moves the routine to its next slot. |

**Claude Desktop.** After adding Nook as an MCP server, each routine you can run appears as a prompt named `routine.<name>` (for example `routine.weekly-review`). Choose it and Claude gets the instructions plus the four-call protocol; say "run it".

**A cron script.** Any MCP-capable agent CLI works. For example, a crontab line that runs a headless agent every weekday at 08:05 (placeholders only):

```sh
5 8 * * 1-5  claude -p "Use the nook MCP server. Call list_due_routines; for each routine with runsAvailable, call start_run, follow its instructions, submit_proposals with the runId, then finish_run with a short summary." --mcp-config /path/to/nook-mcp.json
```

where `nook-mcp.json` names the server `nook` with the URL `https://nook.example/mcp` and the header `Authorization: Bearer <your key>`. Nothing the agent suggests applies until you approve it in the Inbox.

## MCP server

Nook includes an authenticated [Model Context Protocol](https://modelcontextprotocol.io/) server over Streamable HTTP, so trusted AI clients can search and read your notes and files, and write drafts for you to review.

1. Open **Settings → API keys** (`/settings/keys`, which opens the **General** tab) and choose **New key**. Name it, say where it is used (**MCP**, the default; **REST** for scripts and CI, or both; see [The REST API](#the-rest-api)), and build its **Access** one permission at a time (below). Pick when it expires, confirm with your password (and a fresh two-factor code when two-factor is on), and **Create key**. The key is shown in full only once; Nook stores its SHA-256 hash and a short identifying prefix, never the plaintext.
2. Copy the ready-to-paste client configuration. The endpoint is `<your origin>/mcp` (`http://localhost:2026/mcp` for the default deployment) and the key is sent as an `Authorization: Bearer` header.
3. Revoke keys you no longer need from the same screen.

### API keys

**Tabs.** Settings → API keys has three tabs, each with its own URL, and each label shows how many live keys it lists (**Vault 2**). Every key is listed on exactly one tab:

- **General** (`/settings/keys/general`; `/settings/keys` and the old `/settings/mcp` open it, as does an unknown tab): keys for Notes, Files, Tasks, and the other modules. A key that also holds a Chat permission (**Run agents** or **Read agents**) beside other modules stays here and carries an **Agents** chip. **New key** here starts as a general key with **Notes → Read**.
- **Vault** (`/settings/keys/vault`): [vault keys](#vault-keys) (`nkv_…`), with the **Using a vault key** example. **New key** here starts as **Kind: Vault key** with the vault access rows. The tab is hidden while the Vault is off; vault keys made before are then listed under **General** with a **Vault** chip and a note that the Vault is off.
- **Agents** (`/settings/keys/agents`): keys that only run or read agents (Chat → **Run agents** / **Read agents**), including keys that only search chosen knowledge bases. **New key** here starts with one row, **Chat → Run agents** on all agents, and no other module. The tab is hidden while Chat is not available to you.

You can still change **Kind** or the rows in New key; the new key is then listed on the tab it belongs to, and the panel that shows it once says which. The one-time panel, **Edit**, **Rotate**, and **Revoke** work the same on every tab. Switching tabs is a history entry, so Back and Forward move between the tabs you opened and then leave the section; on a phone the tabs are a row under the section header that scrolls sideways, and the back arrow returns to the section list. While a new key is on screen, switching tabs asks first, like leaving the section. Use the arrow keys (and Home or End) to move between tabs and Enter or Space to open one. An integration's page (Team → Integrations) has no tabs: integrations hold neither vault keys nor Chat permissions. Team → Keys is unchanged and filters by **Kind**.

Every key is a **Nook key**: an owner (you), a name, where it is used, an expiry, and a list of **permissions**. Each permission is a module and what the key may do there, for example **Tasks: Write tasks** on **All boards**, or only on the boards you choose. What a key can do is worked out again on every call: its permissions, limited to what your team role allows now, to what team policy allows, and to the items you can open now. A key never does more than you can.

- **The key list** shows each key's surfaces (and, for a key used on both, when it was last used on each), **IP limited** when it only works from certain addresses, its state (**Expires in 12 days**, **No expiry** for keys made without one, **Old key: stops in 23 h** during a rotation, **Blocked by team policy**, **Revoked by an admin**), its permission chips (a permission that grants nothing right now is dashed and says why: your team role, team policy, or no current access), when it was last used, and a 14-day bar chart of calls.
- **Access.** Add one row per permission: **Module**, **Permission**, and **Applies to**: all items (every one you can open, now and later) or **chosen** ones, picked from a list: folders and notes for Notes, folders and files for Files, boards and saved views for Tasks, collections, calendars, routines, and whiteboards, and agents for Chat → Run agents. A folder covers the notes or files directly in it (not its subfolders); a saved view can only be read. A key limited to chosen items works only inside them everywhere: lists, search, Today, cross-board queries, and suggestions show only those items, and anything else answers "not found" as if it did not exist. Tools that make something new outside any chosen item (a top-level folder, a new collection or whiteboard) are not offered to it, and a new note or file must go into a chosen folder. The summary under the rows says what the key can do, and that no key ever shares, manages access or keys, or deletes forever. Options you cannot use say why (**Admins only**, **Your team role reads only**, **Turned off by team policy**).
- **Allowed addresses** (only when your admin has set up `TRUSTED_PROXY_HOPS`; otherwise the form says it is off): up to ten IP addresses or ranges such as `203.0.113.0/24`, one per line. The form marks a wrong line and says why, and shows how an entry is saved (`203.0.113.5/24` becomes the range `203.0.113.0/24`). The key then works only from those addresses, over MCP and REST alike, and a call from anywhere else is refused without saying which addresses are allowed. The key's row then says **Last refused … not allowed from its address**; it also shows refusals because of team policy, a surface the key is not set up for, or an expired key. Admins see that a key is limited, never where to.
- **Saved views** can be chosen only if they are yours: a view someone else shares with you could later be changed to show other boards. A key that holds someone else's view from before this rule shows it as no longer available.
- **Edit** a key to rename it, remove permissions or chosen items, lower **Write** to **Read**, narrow **All boards** to chosen ones, stop using it on one of two surfaces, add or tighten its allowed addresses, or bring its expiry closer. Anything else says **Rotate the key to change this**. Editing never adds access and needs no password; to add access, create a new key.
- **Rotate** gives a new secret and a fresh lifetime, after your password. Because it asks for your password, it can also change the new key's access, where it is used, and its allowed addresses, including widening them. **New key expires** starts on the old key's lifetime (capped by team policy); you may pick another, or **No expiry** when team policy allows it. Choose how long the old key keeps working (now, 1 hour, 24 hours, or 7 days) so you can update your clients; routines bound to the key move to the new one. **Revoke now** on the old key ends that early.
- **Revoke** stops a key at once and withdraws its pending suggestions in the Inbox. Revoked keys stay listed for a week under **Revoked in the last 7 days**; if an admin revoked one, it says so and shows their reason.
- **Expiry.** New keys expire after 90 days unless you choose otherwise; your team decides the longest allowed (365 days by default). **No expiry** sits next to the day choices: a key without one works until you revoke it, and admins see it under the **No expiry** filter in Team → Keys. When team policy requires an expiry, **No expiry** is off and says so, and existing keys without one are **blocked, not revoked**: their row says "Blocked by team policy: keys need an expiry. Rotate it to give it one." They work again once rotated with an expiry, or when an admin turns the rule off. Editing cannot remove a key's expiry (it only brings it closer); rotate instead. An expired key stops working; create a new one or rotate before it ends.

### Vault keys

A **vault key** (`nkv_…`) lets a script, a CI job, or an AI client use vault secrets, and nothing else. Make one in **Settings → API keys → Vault → New key** (`/settings/keys/vault`; it starts as **Kind: Vault key**), or choose **Kind: Vault key** in New key on another tab. It is a separate kind on purpose: a vault key holds only vault access, and an ordinary key can never reach the Vault.

- **Vault access.** Add one row per vault: the **Vault**, the **Environment** (one environment, or **Every environment**: every unprotected one you can read, now and later), and the **Access**: **Read values** or **Read and write values** (set values and create secrets; never delete, clear, or restore). You are offered only the vaults and environments you can reach yourself, at the levels you hold. The key never has more access than you: if you lose access to an environment, or your team role becomes read-only, the key loses it at once; if your account is blocked, the key stops working.
- **Protected environments** (such as Production) are never covered by **Every environment**. To give a key one, turn on **Allow protected environments** and add a row that names it. Creating the key asks for your password, which stands in for the confirmation you give in the app, so the key needs no further step. If an owner marks another environment protected later, every key loses it, even one with a row naming it and **Allow protected environments** on (the setting covers the environments that were protected when you made the key); rotate the key to give it back.
- **Allow MCP clients to read values** is off by default. Without it, an AI client using the key sees vault and secret names, tags, and which environments have values, and can write values if you allowed writing, but never reads a value. With it, `read_secret` returns one environment's value at a time. A key with this setting is an agent's key: keep **Where it is used** on **MCP** (the dialog suggests it), and give scripts and CI their own REST key without the setting. Values an MCP client reads go to that client's AI model provider; prefer the REST API for automation, which reads values without this setting.
- **Expiry.** A vault key always expires: 90 days by default, at most 365 (or less if your team's policy says so). There is no "No expiry" for vault keys.
- **Over REST**, the key works only under `/api/v1/vault`: list vaults (`GET /api/v1/vault/vaults`), one vault's secrets (`…/vaults/<vault-id>/secrets`), one value (`GET …/secrets/<secret-id>/values/<env-id>`), set a value (`PUT` the same path with `{"value": "…", "expectedVersion": 3}`; a stale version changes nothing and answers `VALUE_CHANGED` with the current one), create a secret (`POST …/secrets`), and a value's history (`…/values/<env-id>/versions`, dates and authors only). Settings shows an example under **Using a vault key**. An ordinary key gets `KEY_POLICY` there, and a vault key gets `KEY_POLICY` everywhere else in `/api/v1`.
- **Over MCP**, the key sees only the vault tools: `list_vaults`, `read_vault`, `list_secrets`, `read_secret`, and, with write access, `write_secret_value` and `create_secret`. There are no tools to delete, clear, restore, import, export, share, or manage keys.
- **Limits.** A vault key may read 20 values a minute (1,000 an hour) and write 10 a minute (200 a day); over MCP it may read 60 values an hour. These are lower than yours in the app, and a busy key never uses up your own allowance. When a key hits a limit, it is refused for a while, its Recent activity and the vault's Activity say so, and you get a bell notice (at most once a day per key): if you did not expect that much use, revoke the key. A key that reads more than 500 values in a day gets the same kind of notice even when it never hits a limit.
- **What it did.** A vault key's row shows its vaults and environments and whether it may read values over MCP. **Recent activity** lists what it read and wrote, in which vault and environment (never a value). Each vault's **Activity** shows the key as `key:<name>` (the name it had at the time) with whose key it is; its **Access** page lists **Keys with access** (owners see each key and its levels; every other member sees how many, and their own: members who manage nothing get a read-only Access page with just this section). A key row whose vault or environment is in the Bin says so, and a row beyond what you can reach now (say, **Read and write** after your access became **Read**) is marked; the key keeps what you still have.
- **Edit** a vault key to remove rows, lower **Read and write** to **Read**, change **Every environment** to one environment, or turn either setting off. Changing **Every environment** to one is refused on a key with **Allow protected environments** on (a row naming an environment could reach one protected later); rotate that key instead. Removing the last row that names a protected environment turns **Allow protected environments** off too. **Rotate** (with your password) may change its access and settings, checked against your access now. **Revoke** stops it at once. A revoked key cannot be used again, but values it already read may have been copied: rotate those credentials where they are issued.

### The REST API

Keys whose **Where it is used** includes **REST** call the same tools over plain HTTPS, for scripts, CI jobs, and automation tools that do not speak MCP. Settings → API keys shows an example under **Using the REST API**.

- `GET /api/v1/me` shows what the key can do: its permissions, surfaces, limits, and expiry.
- `GET /api/v1/tools` lists the tools the key may call, each with its input schema (the same list an MCP client sees).
- `POST /api/v1/tools/<name>` runs one tool with a JSON body of its arguments (`{}` for none) and answers with the tool's result as JSON. Errors are JSON `{error, code}` with an HTTP status (404 not found, 403 not allowed, 409 changed since you read it, 429 too many requests with `Retry-After`).

```sh
curl -s -X POST "https://<your nook>/api/v1/tools/list_boards" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{}'
```

**Running agents from scripts.** A key with **Chat → Run agents** (on all your agents, or on the ones you choose under **Chosen agents**; members and admins only) runs your agents over REST, and over MCP with `run_agent`. `GET /api/v1/agents` lists the agents the key may run (name, description, model, and the tools a run may use; never the prompt). `POST /api/v1/agents/<agent-id>/runs` takes `{"input": "…"}` (up to 32 KiB) or a stateless conversation `{"messages": [{"role": "user", "content": "…"}, …]}` (up to 50 turns, 128 KiB, ending with your turn), and optionally `"label"` (60 characters, shown in your Audit log) and `"stream": true`. Without `stream` it waits and answers `{runId, status, output, steps, toolCalls, usage, timings, error}`; with it, the answer is server-sent events (`run`, `delta`, `tool_call`, `tool_result`, `usage`, `error`, and `done` carrying the same result). Disconnecting does not stop a run: `GET /api/v1/agents/<agent-id>/runs/<run-id>` answers its result later, and `POST …/runs/<run-id>/cancel` stops it; both work only with the key that started the run. A run lasts at most 5 minutes, uses only tools that need no confirmation (changes to your Nook become Inbox proposals), never creates a chat, and is kept in your **Audit log**. Each key may run 2 at once, start 20 a minute and 500 a day, and has a daily token budget; past any of them the answer is 429 with `Retry-After`.

```sh
curl -s -X POST "https://<your nook>/api/v1/agents/<agent-id>/runs" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"input": "Summarise the release notes in three bullets.", "label": "nightly"}'

# Streamed: -N shows the events as they arrive.
curl -s -N -X POST "https://<your nook>/api/v1/agents/<agent-id>/runs" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"input": "Summarise the release notes.", "stream": true}'
```

If the key is revoked, narrowed away from the agent, or blocked while a run is going, the run stops at its next step with the error `KEY_INACTIVE`, and the next request answers 401.

Send the key only in the `Authorization` header: a key put in a URL is refused, and if it was a real key you should revoke it because it may now be in logs. Every error has a `code`; a key that does not work for any reason (mistyped, expired, revoked) answers `KEY_INVALID`, and your key's row in Settings says why. Limits apply per surface, so a key used over both MCP and REST gets each minute's limit on each. Your team decides which roles may use REST (**Team → Policies**, admins and members by default). REST and MCP each get their own per-minute limits, so a busy script does not slow your AI client down.

There are twenty-one permissions in all. A key with read permissions plus **Suggest changes** can propose anything it can read and change nothing by itself: a good choice for scheduled agents. Keys created before this release keep exactly what they could do before. Card changes made through a key appear on the board like your own and are recorded in the audit log with the key's id.

**Reviewing an agent's events and rows.** An event or row last changed through a key says **Changed by the MCP key <name>**. The event view's **Undo last change**, and the **Undo** button next to that note in a row, put the previous values back; your own next edit clears the note.

**Reviewing an agent's drafts.** A note whose draft was written through a key shows a **Draft by <key name>** badge in the note list and the editor header, and waits in the **Inbox** as a note draft proposal. Nothing reaches readers until you press **Publish version** (or **Discard** the draft). Leaving such a note never publishes it, even after you edit it; only the Publish button does. (Your own drafts are published automatically when you leave a note only if you edited them in the current session.) If the draft changed after you last saw it, Publish reloads it and asks you to review it first. If you and an agent edit the same draft at once, whoever saves second is told the draft changed instead of overwriting it.

### Attachments over MCP and REST

`list_attachments` and `read_attachment_text` let an agent see the files attached to an item and read the text ones (up to 1 MiB), for example "summarise the agenda attached to this event". They work only with the **read permission of the item's module** (Read calendar for an event, Read notes for a note, Read tasks for a card, Read collections for a row, Read whiteboards, or Read agents on all agents for a chat message) and only for items the key may reach; Read files alone does not open them. `create_text_file` and `begin_upload` accept `purpose: "attachment"` to store the file in your Attachments folder, ready to attach. Files uploaded this way keep their bytes exactly as sent (no photo-location stripping).

`get_event` lists an event's files (name, type, size), and `list_events` gives each occurrence's file count. With **Edit calendar**, `attach_file_to_event` attaches one of those uploads to an event the key's owner may edit, up to 20 per event. It attaches only files uploaded for attaching, never other files from Files, so an agent cannot share your files by attaching them. Removing a file is done in Nook.

### What agents can change (Wave 19)

Every change an agent makes is yours to undo, and none deletes anything forever. Each change is recorded in the audit log with the key's id.

| Tool | Permission | What it changes | How to undo it |
| --- | --- | --- | --- |
| `publish_note_draft` | Publish notes | Publishes a draft of your own note as a new version, but only the exact revision the key read with `get_note_draft` (or wrote). If you changed the draft after the agent read it, nothing is published. | Restore the earlier version from the note's version history. |
| `create_folder` | Write drafts or Write files | Adds a private folder (it never takes its parent's sharing). | Delete the folder in the app. |
| `bin_note`, `bin_card`, `bin_event`, `bin_row` | Move to Bin + the module's write permission | Moves the item (a card with its subtasks) to the Bin for 30 days. A blank note also goes to the Bin, never straight to deletion. | `restore_*`, the Bin, or **Review → Restore all** on the key. |
| `restore_note`, `restore_card`, `restore_event`, `restore_row` | Move to Bin + the module's write permission | Restores an item the key's owner may restore (notes: yours; cards, events, rows: the owner or whoever binned it). | Bin it again. |
| `manage_tags` | Write tasks | Creates a tag (any board member), or renames or recolours one (board owner only). No deletes. | Rename or recolour it back in the app. |
| `set_wip_limit` | Write tasks | Sets or clears a column's WIP limit (board owner only). | Change it back in Board settings. |
| `create_sprint`, `start_sprint` | Write tasks | Adds a planned sprint or starts one (board owner only). Completing a sprint stays in the app. | Edit or delete a planned sprint in the app. |
| `link_attachment` | Write tasks | Attaches one of your own card-attachment files to a card. Files from Files cannot be attached. | Remove the attachment on the card. |
| `create_collection` | Write collections | Adds a private collection from a template or a field list (at most 100). | Delete the collection in the app. |
| `create_text_file`, `begin_upload` + `finish_upload` | Write files | Stores a file in one of your folders (default: Default), private unless that folder is shared. Text up to 1 MiB goes inline; other files go through a one-time upload ticket that works only with the same key, once, for 15 minutes. | Delete the file in Files. |
| `rename_file`, `move_file` | Write files | Renames or moves one of your own files. A move that would change who can see the file is refused. | Rename or move it back. |

**Review and Restore all.** When a key moved anything to the Bin in the last 24 hours, its row in **Settings → API keys** says **Moved 7 items to the Bin today · Review**. **Review** lists what that key binned in the last hour, 24 hours, or 7 days and is still in the Bin, with **Restore all** and **Revoke this key**. Back closes the dialog before it leaves Settings. Keys never gain a new power silently: publishing, file writes, and the Bin each need their own new permission, and the only additions to existing permissions are the tag, WIP, sprint, attachment, and collection tools listed above (their help text in Settings says so).

**Uploading a binary file with `curl`.** After `begin_upload` returns `uploadUrl`, send the bytes with the same key, then call `finish_upload`:

```sh
curl -X PUT "$UPLOAD_URL" -H "Authorization: Bearer $NOOK_KEY" \
  -H "Content-Type: application/octet-stream" --data-binary @photo.jpg
```

**Limits.** Each key can make 120 tool calls and 30 writes a minute, and per day create 200 notes, make 500 task changes, 200 event changes, 100 reminders, 500 row changes, 200 proposals, and 48 routine runs; publish 50 drafts, move 50 items to the Bin (10 a minute), make 20 sprint changes, 100 folder and file-move changes, and 100 file uploads (1 GiB of uploads per account a day). All keys of one account together get 1000 calls and 60 writes a minute, and per day 400 new notes, 1000 task changes, 400 event changes, 200 reminders, 1000 row changes, 400 proposals, and 200 routine runs, with at most 500 proposals waiting at once and each run held to its routine's limit (25 by default, at most 100). Beyond that the client gets `RATE_LIMITED`. Writes are recorded in the audit log with the key's id.

Treat API keys like passwords, use a separate key per client, and give each only the permissions it needs. The text of your notes and files is passed to the client as data. A client that follows instructions hidden in that text is the client's risk, which is why writing is opt-in, publishing and the Bin need their own permissions, and everything an agent does can be undone.
